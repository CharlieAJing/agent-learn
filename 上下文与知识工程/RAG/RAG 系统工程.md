# RAG 系统工程

## 概念

### 定义

**RAG（Retrieval-Augmented Generation，检索增强生成）**先从外部资料中检索证据，再让生成模型结合证据回答问题。检索返回的材料需要经过选择和组织，才能成为模型实际读取的输入。[《Speech and Language Processing》，§11.4](https://web.stanford.edu/~jurafsky/slp3/11.pdf)

**RAG 系统工程**是围绕这条链路建立运行契约，使请求在明确的身份、资源权限、版本、时间和费用边界内执行，并能在故障后定位原因、恢复服务。这里的**契约**指各模块必须遵守的输入、输出、错误和运行约束，不只是一组字段。

本文将检索、生成算法视为已有组件，讨论它们如何组成可运营的系统。**租户**是需要隔离数据、权限或资源的用户组织单位；同一租户中的用户仍可能拥有不同资料权限。**编排**是依据依赖关系安排各模块的调用、等待、取消与结束。

### 核心价值

单个组件能够工作，不代表整条链路能持续交付：身份信息可能在传递中丢失，缓存（保存并复用先前结果）可能复用旧权限下的答案，慢请求可能占满资源，重试还可能放大故障。系统工程把这些隐含条件变成可执行、可检查的规则。

<span style="color: var(--color-red)">权限、预算和版本约束必须贯穿整条请求链路；任何加速、重试或降级路径都不能绕过它们。</span>

### 相似概念

| 名称 | 解决的问题 | 优点与边界 |
| --- | --- | --- |
| 知识工程 | 资料如何成为可信、可检索且可更新的知识 | 决定知识供给；本篇只讨论更新结果怎样安全切换到在线服务 |
| 检索与回答生成 | 如何找到证据并据此形成答案 | 决定单次处理质量；不能独自保证运行可靠性 |
| 效果评估 | 怎样测量回答、检索和证据使用质量 | 判断方案是否更有效；需要题集、标注或其他质量判断依据 |
| 运行观测 | 服务是否按约运行、在哪一步失常 | 快速发现故障；低延迟和低错误率不能证明答案正确 |

> [!faq]- A001：RAG 系统运行成功与回答正确有什么区别？
> 运行成功表示服务遵守约定完成了处理，回答正确还要求事实、条件和证据使用成立。快速返回一个完整答案可能满足部分运行指标，却没有满足质量要求。系统工程和效果评估需要协作，不能互相替代。

## 工作原理

### 基本过程

下面是本文整理的单次在线请求流程。**可信控制信息**由服务端验证或生成，不能从用户文本和检索材料中直接采信。**终态**是请求结束后的明确状态，包括正常完成、受控降级、拒绝、失败和取消。

![[RAG 系统工程-请求运行流程.svg]]

1. **验证身份并建立约束**：验证调用者身份，确定租户、允许的任务、截止时间和资源预算；身份无效时拒绝。过载时按预定准入规则拒绝，而不是无限排队。两类拒绝分别记录。
2. **固定版本并检查缓存**：为请求绑定兼容的资料索引（用于快速查找资料的数据结构）、模型和配置版本。只有当前调用者有权访问且版本适用的缓存结果，才能进入最终检查；未命中或校验失败则继续检索。
3. **取得可用证据**：检索必须带授权范围，即可信规则允许当前调用者访问的资源范围，返回结果再次核对资源权限和适用版本。没有证据是业务状态，依赖故障是运行状态，不能混为同一种空结果。检索错误按预算进行有界恢复；仍无可用证据或不可继续时跳过生成，直接进入第⑤步。
4. **组织输入并生成**：把证据当作待分析数据，按剩余预算组装输入、调用模型。下游调用持续检查取消信号；错误交给有界恢复策略处理。
5. **检查结果并确定终态**：检查输出是否完整、是否满足当前权限与交付契约，标记降级或失败原因。缓存路径同样检查。恢复策略结束后也必须检查已有结果，不能把“停止尝试”直接等同于“没有可用结果”。
6. **交付与记录**：交付允许的内容，记录必要的版本、耗时、费用及终态。拒绝、取消和失败也进入记录，不能只保存成功请求。

图中的恢复不是无限重启：只允许在截止时间和尝试次数内重试可恢复的步骤；否则提交已有结果或错误，由第⑤步判定。整个流程预留最终检查和记录的资源。流式交付即完整答案形成前逐段发送，是第⑤⑥步按输出片段重复执行的变体，其额外约束见“并发、超时、重试与降级”。

### 关键组成与接口

建议把每个接口拆成业务数据与控制信息两部分。**请求标识**用于关联一次用户请求，**尝试标识**区分其内部重试；二者不能混用，否则无法计算重试放大和真实用户影响。模块内部实现可以变化，外部契约必须稳定。

| 模块 | 输入与输出 | 必须守住的接口条件 |
| --- | --- | --- |
| 接入与编排 | 身份凭据、问题 → 验证后的请求上下文 | 租户由验证结果确定；传播截止时间、取消状态和预算 |
| 授权与检索 | 请求上下文、查询 → 授权候选或明确错误 | 返回资源标识、内容版本、定位信息；区分无结果与依赖失败 |
| 证据组织 | 候选 → 模型输入及证据清单 | 保留证据来源、权限依赖与被删除原因；不得默默截断关键条件 |
| 模型适配 | 输入、生成配置 → 输出、结束原因、用量 | 统一限流、超时、截断等错误语义；保留供应方调用标识 |
| 交付与观测 | 输出与过程事件 → 用户结果和运行记录 | 区分正常完成、降级、拒绝、失败、取消；记录不泄露正文 |

接口版本既要检查字段是否可读，也要检查语义是否兼容。改变候选排序方向、错误含义或权限判定时机，即使字段不变，也可能破坏调用者。建议用固定输入和故障条件验证双方共同遵守的契约；不要依赖模型猜测缺失字段。

> [!faq]- A002：为什么仅统一模块的输入输出字段还不够？
> 字段相同仍可能表达不同语义。接口还须约定权限来源、版本适用性、截止时间、取消传播、错误分类与终态。否则调用者可能把依赖失败当作无证据，或把截断输出当作完整回答。

## 能力模型

以下是本文定义的运行诊断模型，不是文献中的质量定律。固定一个观察窗口及服务入口，取入口登记的合法、属于服务范围的逻辑请求组成非空集合，数量为 $N$。每个逻辑请求只计一次，内部重试不增加 $N$；过载拒绝计入，身份无效请求另报。等待这些请求达到终态或截止时间后再统计，避免只统计已快速完成的请求。入口之前的网络不可达不在此分母内，需外部探测另测。

- $N_A$：被接纳执行的请求数，包括可走缓存的请求。
- $N_T$：上述请求中，在约定截止时间内产生最终交付判定的请求数。
- $N_D$：上述请求中，在截止时间前完成契约约定的交付边界且结果合格的请求数。

终态判定不等于交付完成。交付边界须事先指定为服务端完成发送或客户端确认等可观测事件；服务端发送完成不能证明用户实际收到。判定已完成但交付逾期的请求不计入 $N_D$。

合格终态可以包含证据不足时的正确拒答，但不能把所有错误都重新命名为合格拒答。正常答案、允许的降级、合理拒答必须分别列明契约并分组报告。用户主动取消单列；若原统计约定包含它，就保留在 $N$ 中并说明如何判定，不能事后删除不利样本。

定义**按约交付率** $Y=N_D/N$，逐层分解：

$$
\begin{aligned}
Y &= \frac{N_D}{N}\\
&=\frac{N_A}{N}\times\frac{N_D}{N_A}\\
&=\underbrace{\frac{N_A}{N}}_{\text{接纳率}\uparrow}\times\underbrace{\frac{N_T}{N_A}}_{\text{按时判定率}\uparrow}\times\underbrace{\frac{N_D}{N_T}}_{\text{合格交付率}\uparrow}.
\end{aligned}
$$

三项分别定位到流程①、②—⑤、⑤⑥。这是嵌套计数相消的恒等式，不要求独立。箭头仅表示其他因子不变且乘积有改善空间时的方向；提高接纳率可能加重排队并降低后两项，因此不能独立追求最大接纳率。任一条件分母为零时，该条件率记为“不适用”；$N>0$ 且无合格交付时 $Y=0$。窗口内 $N=0$ 时整体率也不定义。

这里的“合格”是按已实施检查得到的判定，是真实正确性与安全性的可观察代理。未发现泄漏不等于证明没有泄漏。建议另设越权、敏感信息暴露等不可接受事件指标；不能用较高交付率抵消安全事件。比较方案时保持分母、流量构成及判定规则一致，并分别查看正常回答占比，防止通过普遍拒答抬高指标。

优化时逐项定位：未接纳的请求先检查容量与准入策略；接纳后未按时判定，检查排队、决定整体完成时间的依赖步骤和重试；已判定却交付逾期或不合格，检查发送耗时、输出完整性以及权限和版本核验。按可减少的失败请求量、对其他因子的损失及实施成本选择干预，不能仅按最低条件率排序。

> [!faq]- A003：按约交付率应如何用于定位瓶颈？
> 先固定请求范围和合格标准，再区分未接纳、接纳后未按时判定、按时判定但交付逾期或不合格三类损失。条件比例用于定位，实际受影响请求数、可修复性和代价决定优先级。条件分母为零不能硬算比例；该指标也不能代替答案质量和安全检查。

## 关键机制

### 身份、资源权限与多用户隔离

**认证**回答“谁在请求”，**授权**回答“此人现在能对哪些资源做什么”。验证登录身份后，仍须对文档、片段及派生答案执行授权。服务访问数据库所用的服务身份不等于用户身份；不能因为服务有权读取，就认为任何调用者有权获得内容。

权限判断存在时间问题：资料和授权关系分散更新时，旧权限可能与新内容相遇。Zanzibar 原始论文把权限决策与内容变化的一致性作为设计目标，使用一致性标记协调读取，说明“有权限系统”并不自动意味着“权限在正确时间生效”。这是特定系统的机制，不是所有授权服务都具备的保证。[Zanzibar，§2.2、§2.4.4](https://www.usenix.org/system/files/atc19-pang.pdf)

本文建议把以下要求作为系统契约：

- **检索前限制范围**：把经过验证的授权条件传入查询；索引不支持所需过滤时，另建可信的候选筛选边界，不能让未授权正文先进入模型。
- **检索后复核资源**：防止索引权限副本过期，尤其是权限刚被撤销时。标题、摘要、计数及引用链接也可能暴露资源存在性，应纳入可见性规则。
- **派生内容继承依赖**：摘要与缓存答案可能依赖多份原文。调用者须满足交付内容所依赖的全部权限，除非存在经过独立批准的公开化规则。
- **明确撤销生效点**：规定权限变更从何时阻止新读取和后续输出，并处理正在执行的请求。复核权限与实际发送之间仍可能发生撤销；若要求严格禁止撤销后交付，需要授权服务和交付端共同提供可实现的时序协议，不能仅承诺“发送前查一次”。
- **故障时关闭受保护路径**：授权状态无法确认时，不把未知当允许。可以返回明确的暂不可用状态，不能回退到未过滤检索。

**逻辑隔离**依靠租户字段、策略和查询过滤分开资源，成本较低但依赖所有访问路径正确执行。**物理隔离**分开存储或计算资源，降低部分交叉影响，但增加部署和维护成本，也不能替代身份验证。数据隔离之外，还要按租户限制并发和费用，避免一方消耗全部共享容量。

> [!faq]- A004：为什么权限检查必须覆盖缓存与派生答案？
> 缓存和派生答案都可能含有受保护原文的信息；它们不是权限豁免对象。原文权限改变后，旧答案可能仍可被命中，因此要保存来源依赖、检查当前权限并执行失效规则。租户相同也不能证明两个用户的文档权限相同。

### 敏感信息保护与提示注入

**提示注入**是攻击者通过输入内容影响模型，使其偏离系统规定的任务或约束；来自检索资料的攻击属于间接提示注入。模型处理自然语言时，业务材料中的指令可能被误当作应执行的指令。OWASP（Open Worldwide Application Security Project，开放全球应用安全项目）的指南把输入处理、权限限制、输出检查及监测组成多层防御，而非保证某一条提示能彻底消除风险。[OWASP，Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

建议先画清信任边界：用户问题、检索正文和外部返回内容都不应直接设置工具权限、租户标识、目标地址或系统策略。**最小权限**指每个执行组件只获得完成当前任务必需的权限。即使模型被诱导，可信程序仍应独立校验资源访问和动作参数；增加输入标签与分隔符有助于表达边界，但不是安全隔离机制。

敏感信息保护要覆盖采集、索引、模型输入、输出、缓存、日志和备份整个生命周期。仅在最终回答脱敏，无法撤回已经发送给外部模型的资料。建议在外发前执行数据分类和最少必要筛选，明确哪些内容可交给哪个处理方；在输出处再核查泄露风险。**脱敏**是删除、遮盖或替换敏感内容，**假名化**是用替代标识保留关联关系；后者不必然使数据无法重新识别。

加密保护传输和存储中的数据，不能阻止已有读取权限的组件误用明文。密钥应独立管理，日志和备份也要有访问期限及删除策略。模型输出中的链接和格式化内容同样是不可信输入，展示端应限制自动加载和危险内容执行；工具执行端不得直接运行生成的操作。

> [!faq]- A005：提示注入防御为什么不能只写一句“忽略资料中的指令”？
> 这仍依赖模型正确区分指令与数据，不能建立强制的权限边界。应由可信程序限制资源和动作，把不可信文本与控制信息分开，并在外发和交付处检查敏感内容。提示约束属于辅助措施。

### 并发、超时、重试与降级

**并发**是同一时间存在多项未完成工作；**背压**是下游处理不过来时向上游限制生产或接纳速度。只有限制同时执行数而不限制等待队列，仍可能耗尽内存并让请求在开始执行前就超时。建议对租户、关键依赖和总体服务分别设置并发上限、等待上限与准入策略。

**截止时间**约束整条请求最晚何时结束；步骤超时只限制一次局部等待。编排器应把剩余时间传到下游，计入排队、连接建立、重试间隔、生成和最终检查。取消请求后，要传播取消信号并核实下游是否实际停止；客户端停止等待不证明远端停止计算或计费。

超时不意味着操作未发生。AWS 对重试的分析指出，多层重试会放大负载，带副作用的操作需要幂等性；**幂等性**指重复请求不会重复产生预期之外的业务效果。**退避**让后续尝试等待更久，**随机抖动**分散同时重试的请求。[AWS，Retries and backoff、Jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

据此，本文建议由明确的一层拥有重试决策，分类处理：临时依赖故障可在预算内重试，权限拒绝和无效输入不自动重试；配额耗尽应等待允许时间或结束，不能紧密循环。写入或扣费动作若支持去重，应在首次发送前持久保存操作标识，并确认外部服务按此标识去重及其有效期；只在本地记住标识不能保证外部不重复执行。模型生成即使没有业务写入，也可能重复计费且产生不同结果。

**熔断**是在依赖持续失常时暂时停止调用，随后用有限探测判断能否恢复；**降级**是在部分能力不可用时交付预先允许的较低能力结果。熔断有助于减轻故障扩散，但其开启、恢复和探测规则必须测试。可减少可选处理，不能关闭权限检查、隐藏证据缺失或把未经核验的模型记忆伪装成检索结果。

**流式输出**在完整答案形成前逐段交付。它改善等待感受，但已发送内容无法由最终检查撤回。系统必须在首段交付前完成身份、证据权限及必要的输入检查；只能在整篇生成后完成的检查，要求缓冲相应内容或放弃即时展示。中途失败须标明未完成，并避免自动重试后把两次输出拼成一个完整答案。首段延迟与最终完成延迟必须分别观测。

> [!faq]- A006：什么时候重试会降低整条 RAG 链路的可靠性？
> 当故障来自过载、各层重复重试、已无剩余预算，或操作的执行结果未知且缺乏外部去重时，重试会放大资源压力或产生重复效果。应先分类错误，再在统一预算内控制尝试次数和等待；流式已交付内容还需要防止重复拼接。

### 缓存与权限、版本失效

**缓存**复用先前计算结果；**缓存键**定义何种请求被视为可复用。语义相近不意味着适用条件相同，尤其不能推导出权限、时效或历史对话相同。**有效期**只是时间边界，不能替代权限撤销和版本检查。

OWASP 的 RAG 安全指南要求按权限范围隔离缓存，并在源内容、删除和权限变化时失效。[OWASP，RAG Security / Section 11: Caching Risks](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html#section-11-caching-risks)

下面是本文的依赖分析建议。实际缓存键可以使用这些依赖的可靠摘要或版本标识，不必保存敏感原文；但摘要相同与访问授权是两件事。

| 缓存对象 | 必须考虑的依赖 | 失效与验证重点 |
| --- | --- | --- |
| 文本编码结果 | 原文内容、编码模型及预处理版本 | 内容或编码配置改变后重算；编码结果也按敏感数据管理 |
| 检索结果 | 查询、授权范围、索引和检索配置版本 | 使用时复核权限；候选标识仍需解析到适用内容 |
| 生成输入或答案 | 问题与相关会话、证据版本、权限依赖、提示和模型配置 | 答案中所有受保护依赖仍可访问，业务时效仍适用 |

**语义缓存**依据语义相似度复用结果，增加误复用的风险，应先在同一授权和版本边界内判断，再独立验证答案适用性。命中率只表示复用频率，不表示复用正确。

知识更新由知识工程负责产出新版本；在线服务负责协同切换。建议先构建完整新索引、验证可读和兼容，再以一个一致的版本入口切换新请求；正在执行的请求按明确规则完成旧版本或重新开始。索引、原文读取和缓存不能在一次请求内任意混搭。权限撤销与资料删除是独立的安全通道，必要时立即阻断交付，不能等普通知识更新完成。

失效通知可能丢失，因此需要读取时检查、周期核对或有界失效策略；具体组合取决于允许的过期窗口。缓存集中失效还会使大量请求同时访问后端，建议控制重建并发。合并相同请求只在权限和输出条件一致时才安全，不能为了减少计算把不同用户合为一个授权主体。

> [!faq]- A007：缓存键包含租户标识后，是否就能安全复用答案？
> 不能。同一租户的成员权限可能不同，权限和资料版本也会随时间变化。答案还依赖问题条件、会话、证据、提示和模型配置。缓存命中后仍须确认当前权限与结果适用性，且处理撤销和删除。

### 日志追踪与运行观测

**指标**汇总一段时间内的数量和分布，**日志**记录离散事件，**链路追踪**关联一次请求跨组件的执行路径。追踪中的 **span（执行片段）**描述一个操作的开始、结束及上下级关系；OpenTelemetry 用共享追踪标识和上下文传播将跨进程片段关联起来。[OpenTelemetry，Traces / Spans](https://opentelemetry.io/docs/concepts/signals/traces/)

Google 的站点可靠性工程教材强调延迟、流量、错误和饱和度四类核心信号，并区分外部可见行为与内部状态。[《Site Reliability Engineering》，Monitoring Distributed Systems / The Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/)

本文建议在这些基础上保留 RAG 特有的关联信息：请求与尝试标识、租户隔离后的身份引用、索引和配置版本、权限判定版本或时间、缓存命中类型、证据标识、各步耗时、用量、截断及结束原因。证据正文和完整提示默认不进入常规日志；确需留存的诊断样本应单独授权、限期保存。追踪标识用于关联，不是访问凭据。

监控要能分开回答：服务有没有接住请求，时间耗在哪里，重试放大了多少工作，哪些版本或租户受到影响。**高基数标签**是取值种类极多的指标标签，把每个请求标识都写成指标标签会增加存储和查询负担；细粒度标识更适合追踪和受控日志。

**采样**只保留部分事件，会使稀有故障漏记。建议将关键安全审计与普通性能追踪分开设计；不能从抽样追踪直接推断完整错误率。监控本身失效也要被检测，诊断数据丢失应可见。运行状态异常后再调取质量评估结果；不能凭“生成成功”推断“证据支持充分”。

> [!faq]- A008：有完整日志，为什么仍需要指标与链路追踪？
> 日志适合查看事件细节，指标适合持续发现总体变化，链路追踪适合定位一次请求跨模块的耗时和因果顺序。三者关联后才能从异常比例找到具体执行路径；同时必须控制敏感数据、标签数量和采样偏差。

### 延迟、成本与容量

端到端延迟由排队、串行步骤、并行等待及交付共同决定。**关键路径**是决定最早完成时间的依赖路径；并行分支全部必须返回时，该部分等待最慢分支，不能把各分支耗时简单相加。若只需要部分分支，须先规定接受条件并取消不再需要的工作。

平均耗时会隐藏慢请求。**分位数**描述分布中的位置，p95 表示约 95% 的观测值不超过该值。各模块 p95 的和通常不是全链路 p95，后者要直接测量。还应把成功和失败请求分开看，避免快速报错让总体延迟看似改善。

容量不是每秒请求数的单一函数。Google 的过载处理章节指出，不同请求消耗差异会让仅按查询数估计容量失准。[《Site Reliability Engineering》，Handling Overload / The Pitfalls of “Queries per Second”](https://sre.google/sre-book/handling-overload/)

本文建议按输入长度、输出长度、检索分支数和重试情况分组压测。**token（词元）**是模型处理文本的基本单位，不能直接等同于汉字或词。生成需要同时考虑输入处理与逐步输出的资源，外部模型还受到请求和词元配额约束。扩容本地编排服务无法突破外部依赖的配额。

成本边界应明确包含查询编码、检索与重排、模型输入输出、重试、缓存、存储、日志，以及按选定口径分摊的索引构建和固定资源。建议同时报告每个入口请求成本、每个合格交付成本和总费用；其中，每个合格交付成本为“选定边界内总费用 ÷ 合格交付数”，零交付时不定义，不能记为零。缓存命中减少的模型费用可能伴随存储、校验和错误复用代价，应看净收益。

每请求设置预算只能限制单个请求，仍需用户、租户和全局预算。并发请求都先检查余额再各自执行，可能共同超支；需要在接纳时预留额度、完成后结算，并处理失败后的释放。供应方最终用量未必立即返回，应明确暂估、对账和允许偏差，不能把本地计数当作精确账单。

> [!faq]- A009：为什么降低平均延迟或单次模型费用，不一定改善系统运行？
> 平均延迟可能因快速失败而下降，模型费用也只是成本的一部分。应检查端到端尾部延迟、合格交付数、重试和共享资源饱和情况，并在统一成本边界内计算总费用与单位交付成本。

### 部署、发布与回滚

**发布单元**是必须共同验证兼容性的一组版本。对 RAG 而言，至少应能定位应用、接口、提示、生成模型、编码模型、检索配置、索引和权限策略；并非每次必须同时修改它们，而是要知道当前组合是什么。**就绪检查**验证实例是否具备接流量条件，不能只检查进程存在。

**灰度发布**先让部分流量运行新版本，在限定时间内与旧版本对照后决定是否扩大。Google 的工作手册将这种有限部署与观察作为降低发布影响的机制。[《The Site Reliability Workbook》，Canarying Releases](https://sre.google/workbook/canarying-releases/)

本文建议依次执行：验证版本组合与资源就绪；运行契约、安全和质量检查；让代表性小范围流量进入新版本；对照错误、延迟、费用及质量；达到事先定义的停止条件即暂停或回退；通过后逐步扩大。**影子流量**是复制请求到新链路但不向用户交付新结果，它仍会处理真实数据和产生费用，必须遵守相同权限、外发限制及预算。

回滚是恢复已知可用的服务组合，不是只切换应用程序。旧程序可能无法读取新索引结构，旧缓存可能仍持有错误答案，因此需要提前验证兼容关系并保留可用资源。**排空**是在停止接纳新请求后，让在途请求完成或受控终止；它避免更新时把半个答案当作完整交付。

<span style="color: var(--color-red)">服务回滚不能撤回已经交付的信息，也不能恢复已经撤销的权限。</span>

权限撤销、资料删除和密钥轮换应持续有效，即使服务回到旧版本。对不可逆的数据迁移，若没有兼容读写或恢复方案，就不能承诺即时回滚。备用模型和异地副本也要验证数据处理边界、权限一致性与契约，不能仅因主服务不可用便自动使用。

> [!faq]- A010：RAG 回滚为什么不能只恢复旧应用版本？
> 应用依赖提示、模型、索引、权限策略和缓存的兼容组合。旧应用与新索引可能不兼容，旧缓存可能带回错误结果；权限撤销和删除又不能被回滚撤销。因此要恢复可用组合，同时保留必须持续生效的安全变更。

## 分类

以下是可组合的部署与执行维度，不是成熟度等级。

| 分类维度 | 类型与机制 | 适用条件 | 优点与代价 |
| --- | --- | --- | --- |
| 服务边界 | 单体内模块调用；独立服务间调用 | 是否需要独立扩容、故障隔离与团队维护 | 单体追踪和部署较简单；拆分服务增加网络、版本和运维负担 |
| 请求生命周期 | 同步等待；异步提交后查询结果 | 是否允许较长处理、断连后继续及稍后取回 | 同步交互直接；异步需要持久状态、去重、取消和结果权限复核 |
| 租户隔离 | 共享资源加策略；独立资源 | 权限复杂度、性能隔离和运维能力 | 共享利用率高；独立隔离较强但资源与维护成本增加 |

异步系统需要记录任务所有者和状态转换，并对结果读取重新授权。提交时有权限，不保证数小时后的领取仍有权限；删除任务记录也不证明后台工作已经停止。选择独立服务或异步执行应解决实际约束，不能把分布式部署本身当成可靠性证明。

> [!faq]- A011：什么时候值得把 RAG 模块拆成独立服务？
> 当独立扩容、故障隔离或维护边界带来的收益超过网络调用、版本兼容和运行观测的新增成本时。应根据瓶颈选择边界；单体中的清晰模块契约也能提供可靠运行的基础。

## 演进与瓶颈

### 关键演进

这里按约束变化解释设计演进，不把它写成所有系统都必须经历的历史阶段。

- **从可运行流程到显式契约**：组件增多后，错误语义、版本和预算不能再依靠隐含约定，运行上下文成为模块之间共同遵守的规则。
- **从单用户正确到多用户隔离**：同一份候选、缓存或日志开始被不同主体访问，必须把权限视为数据流的一部分，而非入口的一次检查。
- **从成功路径到全生命周期**：规模扩大后，排队、取消、重试、更新和发布都会影响交付；需要把正常、失败和恢复路径统一纳入预算和观测。

这些是本文依据前述机制归纳的设计变化。其核心矛盾是：复用和并行提高效率，却扩大共享状态与故障传播；一致性和检查提高可靠性，却消耗时间与资源。取舍应在明确服务契约下进行。

### 当前瓶颈

| 瓶颈 | 根因 | 干预及边界 |
| --- | --- | --- |
| 权限与数据不同步 | 不同副本、缓存和在途请求更新时机不同 | 明确一致性协议与撤销时点；简单缩短缓存期无法保证即时撤销 |
| 尾部延迟与过载相互放大 | 慢请求占资源，排队和重试继续增加负载 | 有界队列、准入和重试预算；代价是部分请求被拒绝 |
| 高命中却复用错误 | 缓存忽略权限、时效或会话条件 | 完整依赖与读取校验；代价是命中率下降、校验开销增加 |
| 可观测却泄露信息 | 诊断需要细节，日志扩大数据副本 | 最少必要记录与受控样本；代价是部分问题较难重现 |
| 快速发布却难恢复 | 依赖组合和数据变化不可逆 | 兼容验证、分步切换与回滚演练；增加发布准备与资源保留 |

> [!faq]- A012：为什么更严格的一致性与更多重试都不能无限增加？
> 更严格的一致性可能增加等待和依赖不可用时的拒绝；重试可能增加过载和重复费用。两者都要服从安全边界、截止时间及资源预算，通过整体按约交付和故障实验判断净影响。

## 使用场景

当系统长期服务多人、资料权限不同、外部模型受配额限制，或需要明确的服务承诺时，应完整设计运行边界。规模较小也不能省略权限与敏感信息保护；可减少的是部署层数和自动化复杂度。

若只有个人离线使用、资料边界单一且可接受手动恢复，清晰的模块接口、版本记录和基本错误处理通常比拆分多服务更有价值。若业务只需返回原文位置，检索服务可能已满足需求；增加生成会引入额外费用、延迟和输出风险。

架构选择应从允许的故障影响、恢复时间、数据处理边界和维护能力出发。**恢复时间目标**规定故障后多久应恢复服务，**恢复点目标**规定可接受的数据丢失时间范围；这两个目标决定备份与恢复方案是否足够。备份存在不等于恢复可用，仍需验证数据、权限和密钥能否共同恢复。

> [!faq]- A013：小规模 RAG 系统可以先省略哪些工程复杂度？
> 可以暂缓独立服务、复杂调度和多地部署，优先保留清晰契约、基本观测与可恢复版本。权限、数据外发边界和失败状态不能因规模小而含混。是否增加复杂度，应由实际服务约束和维护能力决定。

## 评估与干预

### 指标与测评

**SLI（Service Level Indicator，服务水平指标）**是衡量服务表现的观测量；**SLO（Service Level Objective，服务水平目标）**是该指标在规定窗口内要达到的目标。目标还必须说明请求范围与合格判定，不能只有一个百分比。[《Site Reliability Engineering》，Service Level Objectives / Indicators、Objectives](https://sre.google/sre-book/service-level-objectives/)

下表是本文面向运行的测量口径；回答质量的测量方法属于效果评估，运行监控只保存与之关联的版本和请求信息。

| 指标 | 统计与测量方法 | 解读边界 |
| --- | --- | --- |
| 按约交付率 | 按能力模型的固定入口请求集合统计，并按终态分组 | 合格判定是代理；拒答比例和安全事件必须另报 |
| 端到端延迟 | 从约定接收点到首段、最终交付分别计时；按成功与失败分组 | 未完成请求保留为超时或取消，不能从分布中静默删除 |
| 重试放大 | 同窗口实际下游尝试数 ÷ 对应逻辑调用数 | 按依赖分组；分母为零记不适用，多路检索不是同一路的重试 |
| 饱和与排队 | 记录执行槽位占用、等待数、排队时间及配额余额 | 需结合请求工作量，不能只看处理数量 |
| 权限与版本偏差 | 记录越权事件、撤销后交付、版本不兼容及核验覆盖量 | 零发现不证明零风险；漏记和未知状态单列 |
| 单位交付成本 | 选定边界总费用 ÷ 合格交付数，另报总费用与入口数 | 零分母不定义；统一固定成本和索引费用分摊方式 |
| 恢复能力 | 演练记录故障发现、止损、恢复耗时与数据损失 | 仅适用于所演练故障及环境，不能外推所有灾难 |

建议告警绑定可行动的条件和负责人：持续超出交付目标、快速消耗可容忍失败额度、明确越权事件或恢复失败。**错误预算**是目标窗口允许的不合格交付额度，不是允许发生任意安全事件的额度。告警应给出影响范围、版本和处置入口；仅通知数值变化却没有处置动作，会增加噪声。

### 干预与验证

以下是本文建议的开发前验收路径，验证的是约束是否贯穿实现，而非宣称某一架构普遍最佳。

1. **写清契约与基线**：固定版本、请求分布、权限变化规则、费用边界及合格终态，保留现有方案作为对照。
2. **验证接口和隔离**：检查身份缺失、权限撤销、跨用户缓存、派生证据及异步结果读取；验证未授权内容不会进入模型、输出或常规日志。
3. **注入故障**：主动制造依赖超时、限流、中途断连和失效通知丢失，检查预算、取消、重试、降级与记录是否符合约定。确认已执行但回执丢失时不会盲目重复副作用。
4. **施加负载**：在相同请求组成下比较正常、突发和持续过载，观察关键路径、排队、拒绝及费用。确认租户间资源影响受控，并测量容量恢复过程。
5. **演练更新与回滚**：核验新旧版本并存、切换、在途请求排空，以及回滚后的权限撤销和删除仍有效；验证备份实际可恢复。
6. **综合验收再发布**：同时检查按约交付、安全边界、运行代价和独立质量结果；将预定告警和停止条件用于灰度发布。只改善某个过程指标不足以通过验收。

定位时先找最早违反契约的位置，再追到造成它的依赖。权限事故优先止损；容量问题先避免重试和排队继续放大，再调整资源。不能在结果未复核前直接用更多副本或更长超时掩盖根因。

> [!faq]- A014：怎样验证一个运行优化值得上线？
> 在相同请求、版本和统计口径下对照优化前后，检查按约交付、尾部延迟、总费用和隔离边界；再通过故障与回滚演练验证异常路径。独立质量评估不能退化，安全约束不能用效率收益交换。上线时仍需有限范围观察及明确停止条件。
