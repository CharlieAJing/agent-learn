# Agent Harness 工程

## 概念

### 定义

**Agent Harness** 是围绕智能体模型组织输入、工具执行、状态和控制逻辑的运行支撑系统。**Harness 工程**就是设计、验证和持续改进这套系统，使模型提出的行动能够转化为可检查的任务结果。

本文讨论**大语言模型（Large Language Model，LLM）**驱动的智能体。模型负责基于输入生成内容和行动请求；Harness 负责把请求接入实际环境，并决定何时继续、暂停或结束。LangChain 用“Agent = Model + Harness”表达这一分工，并把模型之外的代码、配置和执行逻辑都纳入 Harness。这是宽口径的工程定义，不是所有来源共同采用的严格标准。[LangChain，Can Someone Please Define a “Harness”?](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

本文将直接参与任务执行的控制层作为讨论中心。模型训练、企业整体基础设施不展开；执行环境、存储与监控则按其与任务回路的接口讨论。

<span style="color: var(--color-red)">Harness 工程的核心是把“模型会提出行动”变成“系统能受控执行、继承进展并验证结果”。</span>

### 核心价值

Harness 缓解多步任务中的执行断裂：模型输出行动请求并不等于动作已经发生，一次调用结束也不意味着系统自动保存了进展。必须有程序落实动作、返回观察并安排后续调用，任务才能连续推进。

长任务还会遭遇输入容量限制、工具异常和进程中断。仅增加提示词不能替代状态存储、权限检查和恢复机制。Harness 提供的是让能力可用的条件，并不能保证模型判断正确或工具反馈真实。

### 相似概念

下表按职责比较；同一系统可以同时包含这些部分。

| 名称 | 说明 | 优点 | 局限与适用条件 |
| --- | --- | --- | --- |
| Agent | 围绕目标感知、决策并行动的完整系统 | 能根据反馈调整行动 | 需要环境反馈与验收条件；不等于单个模型 |
| 提示词工程 | 设计模型收到的任务说明和行为指引 | 修改成本低，便于表达意图 | 不能单独强制执行权限；适合改善指令理解 |
| 上下文工程 | 选择、组织和维护本次调用所需信息 | 改善决策的信息供给 | 不覆盖全部执行与恢复职责；适合信息供给瓶颈 |
| Agent 框架 | 提供构建智能体的程序抽象和组件 | 减少重复开发 | 默认行为可能不匹配任务；适合复用组件 |
| 运行时 | 执行程序并管理其生命周期的基础层 | 支撑调度、暂停与恢复 | 不自动定义任务策略；适合承载执行机制 |
| Harness | 将任务策略、输入、工具和运行控制组织为系统 | 能把多项机制连成可运行闭环 | 有维护与评估成本；适合多步、受约束任务 |

框架是构建手段，Harness 是构建出的任务支撑系统；运行时可为它提供底层能力。这是本文采用的职责划分，具体产品可能跨越多层。相关知识见 [[Agent|Agent]]、[[上下文工程|上下文工程]] 与 [[工具调用|工具调用]]。

> [!faq]- A001：Agent Harness 与模型有什么区别？
> 模型根据输入生成判断和行动请求；Harness 组织输入、执行动作、保存状态并控制后续过程。模型是能力组成部分，Harness 是使这些能力能够参与实际任务的运行支撑系统。二者共同影响最终效果。

> [!faq]- A002：为什么改进提示词不能替代 Harness 工程？
> 提示词能引导模型，却不能单独完成外部执行、持久保存状态或强制检查权限。这些职责需要可执行程序和环境支持。提示词本身可以是 Harness 的一部分，但不是它的全部。

## 工作原理

### 基本过程

下图是本文综合整理的任务闭环，不代表某个框架的固定实现。**验收**指依据预先明确的完成条件检查产物和环境状态；**预算**包括允许消耗的调用次数、时间或费用。

![[附件/Agent-Harness-运行闭环.png]]

图中①—⑥对应以下步骤；可编辑图源：[[附件/Agent-Harness-运行闭环.puml|PlantUML 源文件]]。

1. **建立任务约定**：明确目标、允许的行动范围、完成条件与资源预算。恢复旧任务时沿用有效约定，检查环境是否变化。
2. **恢复并组装输入**：读取已保存的进展和实际环境，处理二者冲突，把当前必要信息交给模型。
3. **生成下一步请求**：模型提出行动、补充信息请求或完成声明。请求只是候选决定，不能直接视为执行事实。
4. **检查执行条件**：程序检查参数、权限和剩余行动预算。可修正的拒绝理由反馈给模型；缺少必要授权时暂停；预算耗尽时进入最终验收。
5. **执行、回读并记录**：调用工具，读取结果或错误，记录行动及证据。错误允许在预算内修复；无法确认外部结果时保留“未知”，不能记成“未发生”。
6. **验收与控制退出**：每轮检查完成条件。已达标则交付；未达标但可继续则回到②；缺少输入则保存状态并暂停；无法继续则交付当前结果与未完成项。

模型提出完成、行动预算耗尽或不可恢复错误，都应汇入⑥。系统须预留最终验收与交付所需资源；若无法验收，应报告“结果未确认”，而非断言任务成功或失败。暂停后的恢复从②开始，重新检查当前状态。

### 关键组成

以下是便于设计与排查的职责清单，不要求每项都有独立服务。

| 名称 | 职责与衔接 | 检查方法 |
| --- | --- | --- |
| 任务约定与控制器 | 接收目标，维护执行阶段，安排继续、暂停和退出 | 每种停止原因是否有明确出口 |
| 上下文管理 | 从历史、资料与工具结果中选择本次模型输入 | 关键约束是否保留，证据是否可回查 |
| 工具适配层 | 将模型请求转换为合法工具调用并返回结果 | 参数、权限、错误与返回状态是否明确 |
| 执行环境 | 提供操作所需的程序、文件与外部连接 | 依赖是否可用，访问范围是否受控 |
| 状态存储 | 保存进展、执行位置、行动记录与产物引用 | 进程重启后能否恢复，是否与外部状态一致 |
| 验收与观测 | 检查结果，并记录足以解释执行过程的证据 | 能否区分执行成功、目标完成和证据不足 |

状态至少要区分三类：**任务状态**记录目标和进展；**执行状态**记录运行位置与待恢复操作；**环境状态**是外部世界实际发生的变化。日志是观察记录，摘要是压缩描述，都不天然等于环境事实。保存执行位置与外部动作不一定同时完成；本地没有回执，既可能是动作尚未发生，也可能只是回执尚未保存。

**检查点（Checkpoint）**是可供恢复的执行状态快照。跨任务记忆则保存后续任务可复用的信息，两者用途不同。LangGraph 也区分会话范围的检查点和跨会话的数据存储；仅保存在进程内存中的检查点无法承受进程重启。[LangGraph，Persistence 与 Checkpointer vs. store](https://docs.langchain.com/oss/python/langgraph/persistence)。进一步见 [[Agent Memory|Agent Memory]]。

> [!faq]- A003：模型声明完成或行动预算耗尽时，系统应该怎样退出？
> 先根据完成条件检查实际结果，再决定交付状态。声明完成不证明结果达标，行动预算耗尽也不证明结果未完成。应预留验收资源；验收无法进行时明确结果未确认。需要外部输入才能推进时，保存状态并暂停。

> [!faq]- A004：为什么任务摘要不能替代检查点和环境核验？
> 摘要压缩了任务信息，可能遗漏执行位置与待确认操作。检查点支持恢复程序，但保存检查点与完成外部操作不一定同时发生。恢复时需要结合任务记录、执行状态和环境回读，才能判断哪些动作已经发生、哪些还需继续。

## 能力模型

### 定义与基础公式

本文用**受约束任务成功率**衡量整体能力：在固定任务集与预先规定的预算、权限条件下，按固定验收规则判定通过且全程符合约束的运行数，占全部启动运行数的比例。这是真实任务正确性的可观察代理，验收规则有遗漏时仍可能高估效果。一次运行中的重试和恢复仍算同一次运行；到测评截止时仍暂停或结果未确认的运行不计入成功，并另列状态。

令 $C$ 表示全程满足约束，$R$ 表示截止时结果通过验收。本文成功事件为 $C\cap R$。下面是概率链式法则的诊断模型，不是实测经验公式。$P$ 表示事件发生的概率，$\cap$ 表示两个条件同时成立，条件竖线 $\mid$ 表示“在右侧条件成立时”。

$$
Y=P(C\cap R)
$$

$$
Y=P(C)\times P(R\mid C)
$$

引入 $E$：在满足约束的运行中，截止时已经形成可验收的结果和证据。将“证据充分”作为验收通过的必要条件，即 $R\Rightarrow E$（验收通过必然意味着已有可验收结果），得到：

$$
Y=P(C)\times P(E\mid C)\times P(R\mid C,E)
$$

这里的“结果”包括无需外部动作即可完成的回答，不能把 $E$ 限定为调用了工具。否则，不经工具成功的路径会被遗漏。

### 流程对应与优化方向

在其他因子不变的条件下：

```text
受约束任务成功率↑
= 合规比例↑〔①④⑤〕
× 合规运行中形成可验收结果的比例↑〔②③⑤⑥〕
× 合规且结果可验收时的验收通过率↑〔②③⑤⑥〕
```

上述条件分母须非零。若没有合规运行，或没有合规且可验收的运行，则整体成功率为零，相关条件比例记“不适用”，不能机械计算乘积。

三个比例的分母不同，不能当作独立概率相乘。上述乘法成立是因为逐步附加了条件，不是因为各模块互不影响。

### 优化启示

先检查整体成功率，再查看失败集中在哪里。权限规则过松可能提高产出却破坏合规；规则过严可能降低推进率。增加记录有助于验收，但也消耗预算。因此，局部比例提高不能直接证明整体改善。

按可挽回的失败运行数、修复成本和新增风险确定优先级。进入某一环节的运行数变少，只说明样本量变了，不自动意味着该环节条件通过率下降。改变 Harness 后进入各条件集合的任务也可能变化，所以版本比较必须保留相同任务集的整体指标。

> [!faq]- A005：为什么不能用各模块的独立成功率相乘来预测 Agent 成功率？
> 各模块相互影响，也可能重复执行或被跳过。可靠的分解应以同一批完整运行为样本，明确事件与条件分母。本文依次计算合规、合规时形成可验收结果、前两者成立时验收通过的比例，因此无需独立性假设；比较版本时仍需看固定任务集的整体成功率。

## 关键机制

### 输入管理：把信息保存与信息供给分开

信息存入文件或数据库后，不会自动参与模型判断；必须按当前任务取回并放入输入。上下文管理要保留有效约束、关键决策和证据位置，把暂不需要的细节留在外部。

**上下文压缩**是将已有交互整理成更短的输入，可能丢失细节；**渐进披露**是在需要时才加载相关能力说明或资料。Anthropic 将压缩、结构化笔记和子智能体列为长任务的信息管理方法，并强调按任务选择。[Anthropic，Context engineering for long-horizon tasks](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

据此，本文建议把摘要当作导航，保留原始证据的可定位引用；压缩后核对未完成项、权限边界和待确认结果。目标不是最短输入，而是当前决策所需信息完整且易用。

### 持续执行：保存进展与恢复副作用

**持久执行**指系统在中断后能够依据已保存状态继续任务，而非要求单次模型调用一直运行。长任务还需要明确剩余工作和交接记录。Anthropic 的长任务研究强调初始化工作环境、增量推进和留下可供下一轮理解的进展记录。[Anthropic，Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

上述长任务方案来自特定开发任务的研究，不能直接视为所有任务的最优架构。本文只抽取显式交接、增量推进和结果核验这几项可检验的设计原则。

但保存状态不等于外部动作只发生一次。**副作用**是工具对外部状态产生的改变；**幂等**指同一操作重复执行不会额外改变预期结果。LangGraph 明确指出，节点失败时内部状态回滚不会撤销已经发生的外部副作用，重试需要独立处理去重或幂等。[LangGraph，Fault tolerance，副作用处理部分](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)

本文建议为有副作用的动作记录稳定操作标识、意图和回执。操作标识应在执行前持久保存，或从已保存状态确定性推导；还须确认外部系统支持按该标识去重，不能只靠本地记录防止重复。超时后先查询真实状态，再决定重试；无法查询且无法幂等时，保留未知并请求人工处理。恢复执行位置与恢复外部一致性是两个问题。

### 约束执行：把指引变成可检查的边界

提示词中的“应当遵守”是行为指引；程序中的参数校验、访问控制和预算限制才是实际执行边界。**沙箱**是限制程序可访问资源的隔离环境，但隔离计算资源不等于动作已获用户授权。

本文建议在调用前核对动作、对象与当前授权；对外部资料保留来源标识，避免把读到的文字升级为控制指令。需要人工判断时，暂停必须留下待批准动作和恢复条件。批准应针对具体动作，动作内容变化后须重新判断原批准是否仍有效。

中断机制可以保存状态并等待外部输入，但恢复可能重跑所在节点的部分逻辑。因此，在暂停前已执行的副作用也需要幂等处理。[LangGraph，Interrupts 与 Side effects called before interrupt must be idempotent](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 验收反馈：检查产物，并保留证据链

**执行轨迹（Trace）**是模型调用、工具动作、返回结果和状态变化的关联记录。它帮助解释失败，但轨迹完整并不证明任务正确。

系统需要区分工具报告成功、模型声称完成与结果符合目标。可程序化判断的条件优先使用明确检查；依赖主观质量判断的内容则需要清楚的评分标准，并校准模型评分与人工判断的一致性。Anthropic 的评估指南区分轨迹与最终环境结果，强调二者不能互相替代。[Anthropic，Demystifying evals for AI agents，评估组成部分](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

据此，本文建议让验收读取真实产物与必要的环境状态。失败反馈应指出差距和证据，便于下一轮修复；若验证器本身有遗漏，反复优化也可能只是学会迎合检查。

> [!faq]- A006：为什么有检查点仍可能重复产生外部副作用？
> 外部动作与检查点写入不一定作为一个不可分割的步骤同时完成。动作已经发生、回执尚未保存时中断，恢复后可能再次执行。应结合稳定操作标识、幂等或去重机制和环境查询处理；结果未知时不能把缺失回执当作未执行的证明。

> [!faq]- A007：为什么权限不能只写在系统提示词里？
> 提示词影响模型行为，但不保证每次遵守。工具调用前仍需由程序检查授权、对象和参数，执行环境也要限制访问范围。人工批准需要绑定具体动作，沙箱则限制资源访问；两者分别解决授权与隔离问题。

## 分类

Harness 可按不同维度分类，不能把这些类型当作互斥产品目录。

| 划分依据 | 类型与差异 | 适用条件与主要代价 |
| --- | --- | --- |
| 控制权分配 | 固定流程规定主要路径；模型主导动态选择；混合控制限定阶段、开放局部决策 | 路径越稳定越适合固定流程；动态控制增加灵活性，也增加评估难度 |
| 执行跨度 | 会话内完成；跨会话恢复；持续接收任务 | 跨会话依赖持久状态，持续运行还需资源回收和状态维护 |
| 协作结构 | 单智能体串行推进；多智能体分工汇总 | 分工适合能独立检查的子任务；共享状态和结果整合增加成本 |

本文建议先用最小可用结构建立基线，再按实际失败增加机制。多智能体能隔离不同子任务的输入，但不能自动解决信息遗漏；汇总者仍需获得证据、处理冲突并验收整体结果。它是 Harness 的可选组织方式，不是成熟度标志。

> [!faq]- A008：什么时候值得给 Harness 增加多智能体协作？
> 当工作能拆成依赖较少、结果可独立检查的子任务，且并行收益或输入隔离收益足以覆盖协调成本时。共享状态冲突、重复探索和汇总损失会抵消收益，因此应与单智能体基线比较整体成功率、时间和费用。

## 演进与瓶颈

### 关键演进

以下按职责扩展梳理工程脉络，不声称各做法按此顺序被首次发明，也不表示后一阶段必须替代前一阶段。

1. **从调用模型到组织决策回路**：关注点从一次回答扩展到行动和反馈。Anthropic 在《Building effective agents》（2024）中区分预定工作流与模型动态控制，并主张按需要增加复杂度。[来源，What are agents? 与 When (and when not) to use agents](https://www.anthropic.com/research/building-effective-agents)
2. **从一次会话到可交接的长任务**：上下文限制使连续性成为独立问题。Anthropic 的长任务 Harness 文章（2025）研究通过环境准备、进展记录与增量工作跨越多次上下文窗口。[来源，Environment management](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
3. **从局部技巧到整体系统设计**：LangChain 的 Harness 文章（2026）将模型之外的运行能力放在同一设计范围内，从期望行为倒推所需系统机制。[来源，Working Backwards from Desired Agent Behavior to Harness Engineering](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

这条脉络的关键是评价单位扩大：模型输出只是中间结果，完整运行能否可靠结束才是系统目标。模型能力变化后，应重新评估旧控制规则，避免把临时补救永久堆积成无效复杂度；这是本文的工程判断。

### 当前瓶颈

| 瓶颈与根因 | 改进方向 | 代价与适用边界 |
| --- | --- | --- |
| 长任务丢失约束：输入容量有限，摘要有损 | 分离持久状态与当前输入，保留证据引用并核对交接 | 增加读写与维护；不能保证摘要无误 |
| 异常后重复执行：本地状态与外部副作用不同步 | 操作去重、幂等、回读与明确未知状态 | 受外部系统能力限制；不能仅靠重试解决 |
| 错误被验收为成功：检查条件覆盖不全 | 检查真实结果，扩充失败任务，校准评分 | 验证成本上升；开放任务仍有判断误差 |
| 越做越慢：循环、记录和协作不断增加 | 设置预算，识别重复行动，删除无收益机制 | 过早停止会损失可恢复任务，需检验取舍 |
| 升级后退化：模型与工具接口、任务策略存在适配关系 | 固定任务集回归，保留配置版本与回退方案 | 历史任务覆盖不了所有新分布 |

上述改进是本文按失败机制整理的设计建议，不是保证有效的统一方案。每项都应回到任务级指标验证。

> [!faq]- A009：模型变强后，Harness 的职责会消失吗？
> 不会整体消失。更强模型可能减少某些规划提示和补救回路，但工具执行、持久状态、授权检查与结果验收仍需要系统承载。具体规则应重新评估，保留必要职责，删除已经没有收益的补救机制。

## 使用场景

当任务需要根据执行反馈调整后续动作，且有可操作环境、可保存进展和可检查的完成条件时，Harness 工程具有明确价值。任务越长、外部副作用越多、中断概率越高，对恢复与控制的要求越强。

如果输入已完整、一次调用就能完成，就无需引入复杂回路；如果路径稳定且分支可以写清，固定工作流通常更易验证。Anthropic 同样建议从满足需求的最简单方案开始，权衡智能体带来的质量、延迟与成本变化。[Anthropic，When (and when not) to use agents](https://www.anthropic.com/research/building-effective-agents)

当验收条件无法说明、关键状态不可观察或必要动作未获授权时，增加自主程度不能补齐这些前提。本文建议先完善任务约定和环境接口，再决定开放多少决策权。

> [!faq]- A010：如何判断一个任务需要多复杂的 Harness？
> 先判断是否需要根据反馈动态决定行动，再检查执行跨度、副作用、中断恢复和验收要求。单次生成用简单封装即可；路径稳定时优先固定流程。只有已观察到的需求或失败证明某项机制有价值时，才增加相应复杂度。

## 评估与干预

### 指标与测评

**评估 Harness** 是运行测评任务、记录轨迹、评分与汇总的基础设施；**Agent Harness** 则支撑被测智能体实际行动。评估测到的是模型与 Agent Harness 的组合效果，二者不要混淆。[Anthropic，The structure of an evaluation](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**评估任务集**是用于重复测量系统表现的一组任务及其初始状态、完成标准和约束。测 Harness 时要记录模型版本、提示词、工具定义、环境、预算及评分规则，避免把其他条件的变化误认为 Harness 的改进。

| 指标 | 计算或判定口径 | 解读边界 |
| --- | --- | --- |
| 受约束任务成功率 | 结果通过验收且全程合规的运行数／全部启动运行数 | 整体主指标；需固定任务分布和截止规则 |
| 约束违反率 | 至少发生一次违反约束的运行数／全部启动运行数 | 不只统计成功运行；被正常拦截的越界请求与实际越界分别记录 |
| 恢复成功率 | 故障注入后能正确继续、无重复副作用并最终达标的运行数／注入故障的运行数 | 依赖注入位置与故障类型，不代表所有线上异常 |
| 误报完成率 | 声称完成但复核未达标的运行数／声称完成的运行数 | 依赖复核质量；分母为零时记不适用 |
| 时间与费用 | 统计完整运行，包括失败、重试、验收和恢复 | 报告分布与较慢部分，不能只看成功运行均值 |

同一任务应重复运行，报告波动；只运行一次可能把偶然路径当作稳定能力。Anthropic 区分多次尝试中至少成功一次与多次尝试全部成功的可靠性口径，两者不能混用。[Anthropic，Demystifying evals for AI agents，多次试验与指标部分](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

本文建议为任务集固定截止规则，单列暂停、未完成和结果未确认的数量。过程轨迹用于定位原因，最终验收用于判定结果；成功任务也应抽查约束是否被违反。更一般的评估方法见 [[Evaluation|Evaluation]]。

### 干预与验证

1. **建立基线**：选最小可用系统，固定任务、环境和预算，保留完整运行记录。
2. **定位可修复损失**：按约束违反、结果不可验收、验收未通过分类，回查轨迹，辨认模型判断、输入、工具或运行控制的问题。
3. **提出局部假设**：说明准备改变什么、预期修复哪类失败、可能增加何种代价。优先处理影响大且可检验的问题。
4. **控制变量比较**：只改目标机制，在相同任务与资源条件下重复测量。若必须同时改模型，另设对照以区分贡献。
5. **检查整体取舍**：同时比较成功率、约束违反、时间和费用，并检查旧成功任务是否退化。用未参与调参的任务复核，避免只迎合已知检查。
6. **保留或回退**：收益可重复且代价可接受才保留；记录版本和适用条件，部署后持续收集真实失败并回归验证。

这是本文建议的迭代方法。它把“修复一次表现”变成“验证一项系统改变”，不保证同一改动能迁移到其他模型或任务分布。

<span style="color: var(--color-red)">判断 Harness 改动是否有效，要比较相同条件下的完整任务结果，并同时检查权限、恢复、时间和费用。</span>

> [!faq]- A011：为什么工具调用成功率提高，不足以证明 Harness 变好了？
> 工具调用只是任务中的局部动作，可能执行了错误目标，也可能以额外循环或越权换来更多成功返回。应在固定任务集上测完整运行的受约束成功率，并检查费用、时间、恢复和误报完成情况。轨迹用于解释原因，不能替代结果验收。

> [!faq]- A012：如何把一次失败转化为可验证的 Harness 改进？
> 保存失败任务与初始条件，核对轨迹和实际结果，定位可干预的机制；提出一个具体修改及预期收益，再与基线在相同任务、模型、环境和预算下重复比较。确认整体成功率和约束表现没有被代价抵消，用未参与调参的任务复核，最后记录适用条件并保留回退能力。
