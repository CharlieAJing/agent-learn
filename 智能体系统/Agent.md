# Agent

## 概念

### 定义

**智能体（Agent）** 是在环境中采取行动的主体。环境指它能观察或影响的外部事物和系统。智能体从环境获得观察，由控制器选择行动，再由执行部件把命令转成实际操作。控制器是系统中决定采取什么行动的部分。[Poole 与 Mackworth，《人工智能》§2.1](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html)

**大语言模型智能体（Large Language Model Agent，LLM Agent）** 是由[[LLM|大语言模型]]根据目标和运行反馈决定后续行动的系统。模型在给定权限内选择怎样推进任务，外围程序组织输入、落实动作，并把结果送回决策环节。本文采用这一工程口径。[Anthropic，《构建有效的 Agent》· 什么是 Agent](https://www.anthropic.com/research/building-effective-agents#what-are-agents)

### 核心价值

<span style="color: var(--color-red)">当关键信息要到执行中才能获得、预设流程因而难以写全时，LLM Agent 让原本需要人边做边判断的任务也能由系统推进。</span>

用户说明要达成什么结果、允许做哪些操作。Agent 调用工具获取信息或执行操作，再根据实际结果决定下一步。遇到预先没料到的情况，它可以补查信息或调整做法，继续朝完成条件推进。[Anthropic，《构建有效的 Agent》· Agent](https://www.anthropic.com/research/building-effective-agents#agents)

能交给 Agent 多少工作，取决于它能否执行所需操作、获取可信反馈并核验结果。需要额外授权或人工判断时，系统应把决定交回用户。

### 相似概念

| 名称 | 解决的问题 | 主要做法 | 适用条件与局限 |
| --- | --- | --- | --- |
| 大语言模型 | 理解或生成内容 | 根据输入生成输出 | 适合信息充分的任务。外部执行和状态管理由外围系统提供。 |
| [[工具调用]] | 获取外部信息或执行操作 | 通过约定接口请求外部程序 | 能扩展模型的执行范围，具体能力受接口限制，后续步骤仍由调用方组织。 |
| 固定工作流 | 重复执行已知流程 | 由程序预设步骤、分支和重试规则 | 路径清楚，便于检查和预测。难覆盖预设规则以外的情况。 |
| LLM Agent | 推进路径难以预设的任务 | 模型读取反馈并选择后续行动 | 适合需要动态决策的任务。执行路径、耗时和成本更难预测。 |
| [[RAG\|检索增强生成]] | 为生成补充外部资料 | 检索增强生成（Retrieval-Augmented Generation，RAG）先检索资料，再将其提供给模型 | 能弥补模型缺少资料的问题。质量受检索结果影响，也可作为 Agent 的信息来源。 |

实际系统可以混用这些方式。判断某一环节时，先看程序预设到什么程度。固定工作流也可以让模型在预设路径中选择分支。Agent 则由模型根据运行反馈决定还要做哪些工作，以及如何推进。[Anthropic，《构建有效的 Agent》· 什么是 Agent](https://www.anthropic.com/research/building-effective-agents#what-are-agents)

> [!faq]- A001：LLM Agent 与大语言模型有什么区别？
> 大语言模型提供理解、生成和行动选择能力。LLM Agent 还要围绕目标组织输入、执行行动、获取反馈并推进任务，属于完整系统。

> [!faq]- A002：怎么判断一个多步系统是否采用了 Agent？
> 看模型能否根据运行反馈决定还需要做哪些工作。固定工作流按预设规则安排路径，模型也可以帮助选择已有分支。Agent 把后续工作的选择交给模型，由它依据目标和执行反馈决定怎么推进。两种系统都可以调用工具和进行多轮循环。

## 工作原理

### 基本过程

**执行闭环**指行动结果返回决策环节，并影响后续行动。下面是一种带权限、预算和验收的工程设计。预算规定本次运行可用的时间、调用次数或其他资源。进入流程前，先澄清会影响行动方向的缺失要求。

![[附件/Agent-执行闭环.png]]

图中编号与下文对应。[[附件/Agent-执行闭环.puml|可编辑图源]]

- **① 明确要求**。整理目标、允许采取的行动和验收条件。验收条件规定怎样才算完成。
- **② 整理状态**。读取当前观察和已有记录，区分事实、推测、已完成项和未决事项。任务状态是系统对进度的记录，必要时可重新读取环境信息来核实关键事实。
- **③ 选择下一步**。根据目标与当前状态提出行动，或用现有结果进入验收。
- **④ 检查执行条件**。执行程序校验参数、权限和剩余预算。条件不满足时记录原因，保留尚未执行的状态。
- **⑤ 执行并更新**。调用工具，记录结果或错误，更新任务状态。工具返回的确认不足以判断实际效果时，读取目标状态进行核对。
- **⑥ 验收并决定去向**。核对目标、过程约束和交付内容。通过就交付。还有缺口时，若存在获准且可行的下一步，且有足够行动预算，就继续。其他情况下，报告进展、缺口及需要谁处理。行动预算耗尽时也先验收已有结果，预算应为这次验收预留资源。

教材区分控制器发出的命令和环境中实际发生的动作。[Poole 与 Mackworth，《人工智能》§2.1](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html)

据此，系统可以用回执判断工具报告了什么，再按任务需要核验实际效果。

### 关键组成

| 组成 | 负责什么 | 交给下一环节的信息 |
| --- | --- | --- |
| 目标与约束 | 约定结果、权限、预算和停止条件 | 当前目标、执行边界、验收规则 |
| 决策模型 | 理解当前状态，提出行动或结束 | 动作请求、缺失条件或结束提议 |
| 执行程序 | 依据任务约束检查请求，调用工具并维护循环 | 拒绝原因、执行结果、状态更新 |
| 工具与环境 | 提供观察，执行允许的操作 | 数据、错误或可回读的状态变化 |
| 任务状态 | 保留已知事实、进展和未决事项 | 本轮决策需要的记录与依据 |
| 验收 | 依据任务记录和实际结果核对交付要求 | 通过情况、缺口和交付证据 |

**上下文**是一次模型调用实际收到的信息。**记忆**是保留下来供后续读取的信息。外部记忆被选取并放入上下文后，才会影响本轮决策。长任务可以把关键进度和待办保存在外部，再按需读回。[Anthropic，《Agent 的上下文工程》· 结构化记录](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents#structured-note-taking)

读回后，要用当前信息核对关键记录是否仍然有效。[[Agent Memory]]展开记忆的写入、读取和更新。

这套外围实现可参见 [[Agent Harness 工程]]。Agent 的自主范围由获准工具、执行规则和交接条件共同决定。

> [!faq]- A003：系统应怎样确认任务真的完成？
> 按事先约定的验收条件核对实际结果、过程约束和交付内容。工具回执只能证明其明确报告的事项。工具回执不足以确认实际效果时，再读取外部状态，确认必要的变化是否发生。

> [!faq]- A004：为什么保存过的信息不一定能用于当前决策？
> 记忆需要被查找、选取并放入本轮上下文，模型才能使用。取回后还要确认内容仍然有效，防止过期记录误导决策。

## 能力模型

### 衡量对象

本文用**合格完成率 Y**衡量系统在统一任务条件下完整交付的比例，即通过目标、过程和交付验收的运行数除以全部运行数。验收依据取决于任务类型和可观察证据，结果的可信程度也受验收规则的覆盖范围限制。

先固定非空任务集、验收规则、权限、预算和允许的人工参与范围。每轮每题运行一次，从接到任务计到最终交付、超时或交接。一次运行内的循环、重试与恢复都算在同一次运行里。超时或交接都留在分母，交接符合预定任务目标时可以按该目标验收。

### 从验收条件逐步分解

- **N** 是全部运行数，N > 0。
- **G** 是在约定时限和资源预算内达成目标的运行数。
- **C** 是 G 中也满足过程约束的运行数。
- **D** 是 C 中交付也符合要求的运行数。

D ≤ C ≤ G ≤ N。按集合的包含关系逐步代入：

```text
合格完成率 Y = D / N
合格完成率 Y = (G / N) × (D / G)
合格完成率 Y = (G / N) × (C / G) × (D / C)
合格完成率 Y↑ = 目标达成率↑ × 达标后的过程合规率↑ × 合规后的交付合格率↑
```

首式始终可算。第二式要求 G > 0，第三式还要求 C > 0。遇到零分母时直接报告 Y = 0，将相应条件率记为不可计算。方向箭头表示其他因子保持不变时的影响。

这是按最终验收分层的计数关系。运行路径可以不同，早期错误可以恢复，因子之间也可以相关。用每一步的正确率直接连乘，需要另行处理可变路径、恢复和步骤间的依赖。

### 优化启示

- **N − G** 是未在约定时限和资源预算内达成目标的运行。先从明确要求（①）查到执行结果（⑤），再看验收（⑥）是否发现缺口并引导系统继续处理。
- **G − C** 是达标但过程违规的运行。优先检查执行前的权限校验（④）是否生效，以及工具实际执行的操作（⑤）是否越界。
- **C − D** 是达标且过程合规但交付不合格的运行。先从验收（⑥）确认交付缺少什么，再追溯到相关步骤。

这些差值说明验收损失主要出现在哪里。确定优先级还要回看记录，估计有多少运行能被修复、改动需要多少资源，以及会不会引入其他损失。

> [!faq]- A005：为什么按最终验收分解完成率？
> 一次任务的执行路径和步骤数可能变化，过程中的错误也可能恢复。按目标、过程和交付三个验收条件分层计数，可以对所有运行使用同一标准，再通过运行记录找失败成因。

## 关键机制

### 工具把行动请求转为环境操作

工具负责把可执行的动作提供给系统。工具说明需要讲清用途、参数、返回值和错误的含义。[Anthropic，《为 Agent 编写有效工具》· 工具说明与规格](https://www.anthropic.com/research/writing-tools-for-agents#prompt-engineering-your-tool-descriptions)

返回值应包含判断后续行动所需的信息。[Anthropic，《为 Agent 编写有效工具》· 返回有用信息](https://www.anthropic.com/research/writing-tools-for-agents#returning-meaningful-context-from-your-tools)

工程上可按三个问题检查每次调用。**请求有效**检查格式和参数。**执行允许**检查授权及当前状态是否满足前提。**结果有效**检查操作是否产生了预期效果。

**幂等**指重复执行同一操作时，预期效果与执行一次相同。会改变外部状态的调用超时后，系统应先确认真实状态，再判断是否重试。外部系统支持按操作标识去重时，应在首次发起操作前持久保存标识，重试时沿用同一个。外部结果无法确认时，应把结果保留为未确认。

### 规划与反馈共同决定下一步

**规划**是按目标组织行动和依赖关系。**ReAct（Reasoning and Acting，推理与行动结合）**把语言推理、外部行动和观察放在同一过程中。推理帮助决定查什么或做什么，行动带回观察，观察再帮助更新计划。论文允许按任务需要减少推理出现的频率。[Yao 等，ReAct §2](https://arxiv.org/html/2210.03629v3#S2)

在工程中，计划可随事实更新。先保留目标和约束，每次获得改变判断的重要反馈后，重新检查原计划依赖的条件。遇到互相冲突的观察，优先查可核验的外部状态。

### 反思改变后续输入，不必改变模型参数

**反思**指根据一次尝试的反馈归纳原因并提出下次改法。Reflexion 将评价结果转成文字反思，保存在记忆中，供后续尝试读取。这个机制通过改变后续输入影响行为，模型参数可保持固定。[Shinn 等，Reflexion §3](https://arxiv.org/html/2303.11366v2#S3)

采用这种做法时，应把反思与可核查的失败证据关联起来，再用下一次执行验证改法。反馈失真或归因错误时，反思可能让相同错误延续下去。

> [!faq]- A006：为什么工具请求有效还要检查执行和结果？
> 参数有效说明程序能理解请求。授权和状态检查才能决定当时是否允许执行。操作完成后，还要用实际结果确认是否产生了所需效果。

> [!faq]- A007：什么时候反思可能改善后续尝试？
> 系统拿到可信反馈、能定位可改的原因，并能让下一次尝试读到相关改法时，反思才有机会改变行动。最终还需要看后续行为和实际结果。

## 分类

LLM Agent 的工程设计可从四个维度选择。各维度可以组合。

| 划分维度 | 常见选择 | 取舍 |
| --- | --- | --- |
| 决策时机 | 看到反馈后即时决策，或先规划再按反馈更新 | 即时决策适合逐步揭示信息。预先规划便于协调已知依赖，还需为计划失效留出口。 |
| 授权范围 | 生成建议，在限定范围内执行，在关键节点交回人工 | 依据动作影响、可恢复性和可核验性决定权限。 |
| 状态保留 | 仅保存本次运行状态，或在后续运行复用记忆 | 复用能减少重复调查，也带来维护和核对成本。 |
| 协作结构 | 单 Agent 推进，或由多个 Agent 分工与汇总 | 独立子任务可并行。共享状态多时，沟通、冲突处理和结果整合的成本更高。 |

**多 Agent 系统**由多个智能体协作推进，多个角色可以使用同一个大语言模型。并行探索的收益取决于子任务的独立性、上下文能否拆开，以及负责人能否可靠核验并合并结果。[Anthropic，《我们如何构建多 Agent 研究系统》· 多 Agent 的收益](https://www.anthropic.com/research/multi-agent-research-system#benefits-of-a-multi-agent-system)

> [!faq]- A008：什么条件下值得引入多个 Agent？
> 子任务可以相对独立推进，分工后的结果能可靠核验与合并，而且收益高于新增的调用、沟通与协调开销。

## 演进与瓶颈

### 关键演进

- **状态与反馈成为控制基础**。传统智能体已经根据观察选择行动。语言模型进入这一结构后，自然语言目标、工具说明和观察结果可参与同一个决策过程。这增加了系统处理开放任务的灵活性，实际执行与结果仍要通过环境验证。[Poole 与 Mackworth，《人工智能》§2.1](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html) [Yao 等，ReAct §2](https://arxiv.org/html/2210.03629v3#S2)
- **失败反馈进入后续尝试（2023）**。Reflexion 将文字反思保留给下一次尝试，使失败反馈能跨尝试影响行动。它可能改善目标达成率，效果取决于反馈和归因。[Shinn 等，Reflexion §3](https://arxiv.org/html/2303.11366v2#S3)
- **测评关注重复可靠性（2024）**。τ-bench（Tool-Agent-User Interaction，工具—智能体—用户交互基准）将工具、模拟用户和领域规则放在同一任务中，并用重复运行评估可靠性。[Yao 等，τ-bench §3](https://arxiv.org/html/2406.12045v1#S3)
- **长任务强调维持可用状态（2025）**。压缩历史和结构化记录有助于在输入受限时保留关键事实。保留内容的完整程度会影响后续决策。[Anthropic，《Agent 的上下文工程》· 长任务](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents#context-engineering-for-long-horizon-tasks)

### 当前瓶颈

这些瓶颈来自系统的不同环节，出现频率和影响需要在目标任务上测量。

| 可观察问题 | 可能的成因 | 干预和验证 |
| --- | --- | --- |
| 交付偏离目标 | 目标或验收条件含糊，系统对完成的理解与用户不同 | 先补齐会影响行动的缺失要求。检查偏离项是否减少，以及前期沟通是否过重。 |
| 重复动作或沿用旧结论 | 反馈没有更新状态，或关键记录没有进入当前上下文 | 比对最近观察和行动所用信息。保留依据、更新时间和未决项，检查重复动作是否减少。 |
| 外部操作重复或漏做 | 执行结果不明，重试前无法确定真实状态 | 工具支持时回读实际状态或使用去重标识。限制重试次数，检查是否发生重复或漏做。 |
| 未完成时宣称成功 | 验收依赖模型自报或工具回执，关键要求缺少可观察证据 | 对关键要求补充独立检查。观察声称成功的运行中有多少未通过验收。 |
| 达标但过程违规 | 权限约束仅出现在给模型的说明里，执行程序没有检查 | 在执行入口落实限制。用运行记录和外部状态回查违规是否减少。 |
| 成本持续增加、进展停滞 | 系统重复使用同一证据和策略，或没有明确退出条件 | 检查每轮是否取得新信息或推进验收。设定预算和交接条件，同时比较完成率与成本。 |

> [!faq]- A009：大语言模型主要改变了传统智能体的哪一部分？
> 主要改变了控制器的决策方式，使自然语言目标、工具说明和观察结果能参与动作选择。系统仍依靠执行和环境反馈才能更新状态并验证效果。

> [!faq]- A010：Agent 一直重复同一个动作，应先查什么？
> 先核对动作是否实际生效、反馈是否返回，以及新的观察有没有进入下一轮决策。按原因修复工具、状态或动作选择，再用进展判断、预算和交接机制限制无效循环。

## 使用场景

Agent 尤其适合**后续决策依赖执行中新获得的信息、所需行动可在授权范围内完成、实际结果可验收**的任务。决策自由度增加后，还应按任务结果判断收益能否覆盖额外的调用、等待和人工核查成本。[Anthropic，《构建有效的 Agent》· 何时采用](https://www.anthropic.com/research/building-effective-agents#when-and-when-not-to-use-agents)

| 任务条件 | 优先考虑 |
| --- | --- |
| 当前信息足够，交付是内容生成或判断 | 单次模型调用 |
| 主要缺口是外部资料 | 检索增强生成 |
| 步骤和异常分支稳定，可以预先定义 | 固定工作流 |
| 下一步取决于执行反馈，路径难以事先写全 | 在限定权限与预算下运行 Agent |

当结果难以验证或错误难以恢复时，缩小自动行动范围，将必要的验收或高影响决定交给人。对照不同系统时，使用同一用户目标与验收条件，并计入真实人力与运行成本。

> [!faq]- A011：任务很复杂，就值得使用 Agent 吗？
> 要看关键步骤能否事先规定，以及执行中新获得的信息是否改变后续行动。路径稳定时可采用工作流。需要动态决策且具备可用工具、可信反馈和验收方法时，再比较减少的人工工作与新增成本。

## 评估与干预

### 指标与测评

**运行轨迹**是一次任务的可记录事件，包括模型发出的请求、工具结果和状态变化。**最终状态**是运行结束后实际形成的结果。[Anthropic，《理解 Agent 测评》· 测评结构](https://www.anthropic.com/research/demystifying-evals-for-ai-agents#the-structure-of-an-evaluation)

验收可结合两者：用最终状态检查任务效果，用轨迹检查过程约束、定位原因。Anthropic 将评分方式分为程序、模型和人工三类。模型评分需要与人工判定对照，以了解偏差并据此调整评分规则。[Anthropic，《理解 Agent 测评》· 评分方式](https://www.anthropic.com/research/demystifying-evals-for-ai-agents#types-of-graders-for-agents)

| 指标 | 计数或判定口径 | 用途 |
| --- | --- | --- |
| 合格完成率 | D / N | 衡量约定条件下的完整交付 |
| 三类验收损失 | N − G、G − C、C − D | 判断哪些验收环节损失较多 |
| 约束违反率 | 至少发生一次指定违规的运行数 / 全部运行数 | 监测越界，包括最终仍达标的运行 |
| 成功误报率 | 自报完成而验收失败的运行数 / 自报完成的运行数 | 检查完成判断是否可信 |
| 人工介入成本 | 人工实际用时 / 全部运行数，同时记录需人工介入的比例 | 验证是否减少人的实际负担 |
| 单位合格成本 | 全部运行的总成本 / D | 判断额外执行成本是否换来足够多的合格结果 |

比例分母为零时报告不可计算。记录任务构成、环境版本、模型和工具设置、预算及人工参与规则。重复测评时，每轮可分别计算 Y。汇总时按全部运行重新计算 N、G、C、D。

τ-bench 的 **pass^k** 衡量同一道任务独立尝试 k 次全部成功的概率，再在任务集上平均。**pass@k** 衡量同一道任务独立尝试 k 次至少成功一次的概率，再在任务集上平均。对单题，若每次成功概率为 p，且尝试独立、条件相同，两者分别是 p 的 k 次方与 1 − (1 − p) 的 k 次方。

任务难度可以不同，应先按单题计算或估计，再汇总。比较两个系统时，各题成功概率可能有升有降，所以当两项指标采用相同的 k 且 k > 1 时，任务集平均值的变化方向仍可能不同。k = 1 时，两项指标都等于单次成功率的任务平均。[Yao 等，τ-bench §3 · Metrics](https://arxiv.org/html/2406.12045v1#S3)

τ-bench 用最终数据库状态和必要回复信息判断成功，作者指出该规则可能漏掉过程违规。[Yao 等，τ-bench §3 · Reward](https://arxiv.org/html/2406.12045v1#S3)

如果授权或其他过程约束影响交付是否合格，测评时应在结果核验之外再检查相应的运行轨迹。

### 干预与验证

1. **建立基线**。基线是用来比较改动的初始表现。固定代表任务、初始环境和验收方法，记录成功与失败运行的结果、人工介入和成本。
2. **定位失败成因**。从验收损失回查实际轨迹，判断首次发现的缺口如何形成、有没有恢复机会、需要改动哪个环节。
3. **检验一个主要改变**。保持其他条件尽量一致。每次测评重置环境，并重复运行，避免前次状态影响结果。
4. **计算整体收益**。在同一任务集上比较新增合格与原先合格项目的回退，同时检查约束违反、人工用时和单位合格成本。某一环节改善后，整体结果仍可能因其他环节退步而下降。
5. **核验适用范围**。用未参与调优的任务再测一次。若改动只对调过的任务有效，或新增开销抵消收益，应根据这些证据限制适用范围。

> [!faq]- A012：任务集相同、k 相同时，pass@k 提高，pass^k 也会提高吗？
> 当 k > 1 时，两者的变化方向可能不同。它们分别按单题至少成功一次和全部成功的概率取平均，各题的成功概率可能有升有降。评估同样次数下连续成功的稳定性，应直接比较 pass^k。

> [!faq]- A013：如何验证某项改动确实提高了 Agent 的整体表现？
> 用同一任务集、初始环境、预算和验收方法比较改动前后的重复结果，尽量控制其他改变。核对收益和回退，并同时看过程违规、人工用时与运行成本，最后用未调过的任务复测。
