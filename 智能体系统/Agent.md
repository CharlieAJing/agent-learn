# Agent

## 概念

### 定义

**智能体（Agent）**是能够在<font color="#c00000">环境</font>中采取行动的主体。环境是它能观察或影响的外部世界，也可以完全由软件构成。理解智能体，先分清三个对象：环境实际处于什么状态，智能体能观察到什么，它又能采取什么行动。观察可能滞后或不完整。[Poole 与 Mackworth，《人工智能：计算智能体基础》第 2.1 节](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html)

**大语言模型（Large Language Model，LLM）驱动的智能体**。在一种常用的工程定义下，人给出目标和可用权限，模型根据当前信息决定下一步，程序执行获准的动作，再把结果交给模型。[Anthropic，《构建有效的智能体》“什么是智能体”](https://www.anthropic.com/research/building-effective-agents)

广义定义关心主体怎样与环境交互。LLM Agent讨论其中由 LLM 根据反馈安排行动路径的一类系统。

### 核心价值

一次模型调用只能依据当时已有的信息给出答复，而有些任务必须先行动、看到结果，才知道下一步该怎么做。Agent 让模型能够借助工具执行行动，再根据实际结果调整计划，从而把用户委托的目标推进到可以验收的结果。

这种能力在**目标明确、步骤需要边做边调整**时尤其有价值。用户给出目标、权限和完成标准后，Agent 可以检查每次行动还留下哪些差距，在授权范围内继续处理。这样，用户就能把逐步执行和判断下一步的工作一并委托出去，只在缺少关键信息或需要额外授权时介入。

> [!faq]- A 002：为什么模型能给出计划，有些任务仍需要 Agent？  
> 计划依据的是行动前掌握的信息。当前一步的实际结果决定后一步怎么走时，还需要执行动作、观察变化并重新判断。Agent 把这些环节连起来，使系统能在授权范围内持续推进任务，直到结果可验收，或需要用户介入。

### 相似概念

Agent 与 工作流：如果模型只在<span style="color: var(--color-red)">预先写好的分支</span>中选择，路径仍由工作流规定。如果模型能根据新观察自行安排后续行动，系统就有了 <font color="#c00000">Agent 的动态决策</font>能力。一个系统可以把<font color="#c00000">固定流程</font>和局部的<font color="#c00000">动态决策</font>组合起来。[Anthropic，《构建有效的智能体》“工作流与智能体”](https://www.anthropic.com/research/building-effective-agents)

| 类型 | 一句话说明 | 优点 | 局限 | 适用场景 |
| --- | --- | --- | --- | --- |
| 单次模型调用 | 模型根据给定输入生成一次结果 | 等待时间短 | 无后续轮次利用执行反馈 | 摘要、分类 |
| 模型调用链（LLM Chain） | 按预设顺序调用模型，上一步的输出传给下一步 | 各步便于单独检查 | 步骤顺序固定 | 先提取要点，再生成文稿 |
| 工作流（Workflow） | 程序定义节点、分支和执行顺序 | 路径清楚，便于验证 | 新路径需要调整流程 | 审批、业务自动化 |
| LLM Agent | 模型依据目标和新观察动态选择行动 | 可随结果调整步骤 | 轮数、耗时较难预估 | 编程、研究、探索性任务 |
| 多智能体（Multi-Agent） | 多个 Agent 分工、协作或委派任务 | 独立子任务可并行 | 增加交接与整合成本 | 可分工的开发与评审 |

这些方式可以组合：工作流中的一个节点可以运行 Agent，Agent 也可以把子任务委派给其他 Agent。

> [!faq]- A001：有工具、有分支的系统就属于 LLM Agent 吗？
> 看谁决定执行路径。程序预先规定分支和后续步骤，模型即使负责判断分支，仍可属于工作流。如果模型在执行中形成计划，能够在权限内调整动作的先后、增加步骤或结束任务，这就具备本文讨论的 Agent 特征。

> [!faq]- A002：为什么让模型接收行动反馈能减少用户的工作？
> 部分决策所需的信息要等行动后才出现。只要反馈足以指导选择，系统又有权限推进，模型就能接过原本由用户完成的查看结果和决定下一步的工作。

## 工作原理

![[Agent-基本执行流程.svg|800]]

1. **用户输入 / 系统触发。** 接收/触发任务，包括目标和约束。

- 目标：做什么？
- 约束：
    - 按内容：
        - **范围 / 边界**：处理哪些对象？做到哪里为止？
        - 权限、资源等。
    - 按强度：
        - **硬约束**：哪些必须？哪些禁止？哪些要先满足条件？
        - **软偏好**：哪些推荐？哪些少用？
    
2. **构建上下文。** 运行程序按需组织以下信息，作为模型本轮决策的输入：

   - **系统指令**：模型承担的角色（负责什么）和需要遵守的规则（应当怎么做）。
   - **当前任务**
   - **相关历史消息**
   - **工具调用与结果**：已经请求了什么操作，返回了哪些数据、状态或错误。
   - **按需取回的记忆**：从已保存的记录中选出的相关事实、偏好或经验。
   - **可用工具说明**：本轮可以调用哪些工具，各自有什么用途、需要哪些参数。

3. **LLM 推理与决策。** 模型根据运行程序提供的上下文，判断当前进展并选择下一步。

   - **推理：还差什么？** 对照目标与约束，判断哪些条件已满足、还缺哪些信息或行动。若已有工具反馈，用实际结果更新判断。
   - **决策：接下来做什么？** 依据充分时，模型直接作答。需要查询信息或执行操作时，模型选定工具并生成参数，由运行程序调用工具。若关键信息只有用户能提供，模型就提出具体问题，等用户补充后再判断。

2. **调用工具。** 运行程序检查请求是否在<font color="#c00000">授权</font>范围内，再把参数交给工具执行。动作是否成功，要看执行结果。
3. **观察结果。** 运行程序把返回的数据、状态或错误与原请求一起加入上下文。若任务未完成且仍可继续，模型根据工具反馈重新判断原先缺少的条件是否已经满足。[LangChain 的工具调用循环](https://reference.langchain.com/python/langchain/agents/factory/create_agent)
4. **最终输出。** 有依据确认目标达成时，交付答案或产物。若已无法推进或达到运行上限，则根据已有证据报告进展、停止原因和待确认事项。

> [!faq]- A003：工具已经返回结果，为什么还要把它交回模型？
> 工具返回的是一次行动的结果。模型还要结合任务目标判断，这个结果是否解决了原本的问题。解决了就可以作答，仍有缺口就需要调整下一步；若运行已达上限，就依据已有结果报告进展。

## 组成

### 静态定义：构建 Agent 要指定什么？

![[Agent-定义组成.png|400]]

- **模型**是负责理解任务、推理和选择行动的语言模型。
- **指令**写明 Agent 负责什么、应遵循哪些规则、交付什么。运行时，模型依据这些指令处理具体任务。
- **工具**提供模型可以请求的操作。每项工具都需要说明用途和参数，并关联到可执行的函数或服务。[OpenAI《构建智能体实践指南》](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

### 运行协作：模型、运行程序和工具如何配合？

![[Agent-运行时信息流.png|640]]

- **模型**读取运行程序提供的上下文，决定直接答复、询问用户或请求工具。复杂任务中，模型可以拆分目标，再根据反馈调整计划。参见 [[规划与执行]]。
- **运行程序（编排层）**把指令、任务和已有进展交给模型，检查工具请求的权限，发起调用，并把结果交回模型。它维护本次任务的状态，需要以往的信息时，再从长期记忆中取回相关记录。参见 [[Agent Harness 工程]]、[[Agent Memory]]。
- **工具**接收运行程序传入的参数，在授权范围内读取数据或执行操作，返回结果或错误。它依赖哪些数据源、外部服务和访问凭据，取决于具体操作。参见 [[工具调用]]。

这三个构件的分工是<span style="color: var(--color-red)">模型选择行动，运行程序组织调用，工具执行操作</span>。[Google Cloud《生成式 AI 术语表》](https://docs.cloud.google.com/docs/ai-ml/generative-ai/glossary#ai-agents)

> [!faq]- AB01：模型能看到工具说明，是否意味着它有权执行该操作？
> 工具说明让模型知道可以提出什么请求。运行程序按本次任务的授权检查请求，通过后才调用工具。

> [!faq]- A004：为什么保存了记忆，模型仍可能作出过时的判断？
> 运行程序需要先取回相关记录，把它放入本轮上下文，模型才能使用。即使取回了记录，涉及可能已变化的事实，仍须核实当前状态。

## 分类

### 按决策主体数量划分

#### 多智能体

两个或更多 Agent 各自选择行动，并通过通信或共享环境相互影响。[Poole 与 Mackworth《人工智能》第 14.1 节](https://artint.info/3e/html/ArtInt3e.Ch14.S1.html)

- **优点**
  - **高内聚低耦合**：各主体只需处理职责范围内的指令、资料和工具，减少无关干扰。
  - **并行提效**：多个分支都需要根据新线索持续判断时，各主体可以同时推进。
  - **故障隔离**：一个主体的误操作可被限制在本分支，其他分支仍能推进。
  - **上下文隔离，减少干扰和重复输入**：各 Agent 按需读取资料，降低误用其他分支信息的风险，也省去反复传入无关记录的 token。局限：跨分支证据仍要传全，协调开销可能抵消节省。
- **适用场景**：子任务可独立推进、分别验收，且分工收益足以覆盖协调成本，或需模拟多个主体间的互动。

#### 单智能体

单智能体系统由一个 Agent 根据任务目标和执行反馈持续决定下一步，可以多次调用模型或工具。

- **优点**
  - **上下文连续**：后续判断依赖前一步的证据时，同一 Agent 可以沿用已有记录，减少交接时遗漏条件或重复调查的机会。
  - **协调开销低**：步骤紧密相依时，拿到结果即可继续，省去主体间的分派、同步和汇总。若多个独立分支都需要持续决策，集中处理可能形成瓶颈。
  - **统一取舍**：多项操作共用预算或会改变同一状态时，一个 Agent 能对照整体目标安排先后，减少局部计划之间的冲突。
  - **编排简单，便于排错**：只需维护一条决策循环。保留每轮输入、动作和结果后，可以沿同一条记录定位首次偏差，省去跨主体核对消息的工作。
- **代价**：任务越长、分支越多，整理线索和跟踪进度的负担越重。
- **适用场景**：各步骤共享大量背景，下一步取决于刚取得的结果，且一个主体具备推进任务所需的信息和权限。

> [!faq]- A007：怎样判断一个子任务值得交给另一个 Agent？
> 看接手者凭约定的目标、输入和权限能否自行判断下一步，以及结果能否独立验收。若每遇到新线索都要原 Agent 拍板，保留一个决策主体通常更省事。能独立推进时，再比较分工收益与交接成本。

## 演进与瓶颈

### 关键演进

- **根据行动结果调整计划：ReAct（2022）**。当下一步取决于外部状态时，模型需要先取得事实。ReAct 让模型在推理中选择行动，再用行动返回的观察更新计划。由此，Agent 可以在执行中修正最初的假设。但如果观察本身有误，后续决策也可能沿着错误方向继续。[ReAct，第 2、3 节](https://arxiv.org/abs/2210.03629)
- **从单次成功到重复验收：τ-bench（2024）**。Agent 能调用工具后，答复听起来合理，仍可能没有办成用户要求的事。τ-bench 在任务结束后核对数据库状态和回复中的必要信息，并从相同起点重复运行。在论文当时的零售实验中，同一任务连续八次全部成功的指标低于 25%。这说明，偶尔能完成任务，距离可以稳定委托还有差距。[τ-bench，第 3、5 节](https://arxiv.org/html/2406.12045v1#S3)

### 当前瓶颈

**结果正确，过程仍可能违规。** 经过用户确认的退款和跳过确认的退款，可以产生相同的数据库终态。只看最终余额，无法判断是否取得了授权。[τ-bench，第 3 节](https://arxiv.org/html/2406.12045v1#S3)

- **方法**：把过程要求落实到受约束的动作上。执行前检查必要条件，满足后才放行，并记录放行依据。
- **代价**：每增加一项检查，就多一条需要维护的规则。需要人工确认时，任务还要等待。

**正确证据在后续决策中丢失。** 长任务需要压缩历史。摘要可能保留一条规则，却删掉它的例外条件，导致模型在下一轮用错规则。[Anthropic《智能体的上下文工程》](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

- **方法**：按后续决策的需要保留信息。会改变选择的条件随结论一起保留，其余细节保留来源，按需取回。
- **代价**：随结论保留的细节越多，越占用上下文。压缩越多，后续判断越依赖检索，漏取关键条件的风险也越高。

**未经确认的判断被当成事实。** 工具返回「请求已受理」，只能证明请求已被接收。若任务记录直接写成「操作已完成」，后续即使准确取回这条记录，仍会依据错误状态行动。[HTTP 语义：202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted)

- **方法**：区分已观察到的事实和仍待验证的推断。当下一步行动或最终交付依赖某项推断时，先取得能直接验证它的证据。
- **代价**：逐项核验会增加调用和等待。推迟核验可以减少无用检查，但若放任后续步骤依赖未经验证的判断，一旦判断有误，返工范围就会扩大。

> [!faq]- A008：怎样判断一次失败该改进记忆，还是改进验证？
> 找到第一次做错决定的那一轮，对照原始证据、任务记录和模型实际看到的上下文。证据原本正确，却在摘要或取回时缺失，改进记忆；记录从一开始就把推测写成事实，改进验证。把错误记录保存得更完整，只会让同一个错误更容易延续。

## 使用场景

判断一个任务是否适合用 Agent，先看**拿到中间结果后，能否事先规定下一步怎么做**。如果反馈与动作的对应关系清楚，工作流就能处理。如果每次得到的新线索都会影响接下来查什么、试什么，而且行动结果能帮助判断是否更接近目标，就适合用 Agent。

以构建失败为例，同一个任务可以有三种处理方式：

- **固定流程**。日志显示依赖下载超时，恢复步骤已经明确，工作流可以按规则重试并检查构建结果。
- **自主排查**。日志只显示测试失败，原因可能出在代码、配置或环境。Agent 可以先复现失败，再根据观察决定检查哪一处，最后重新运行测试验证判断。
- **常规自动处理，例外交给 Agent**。工作流处理已知错误，把无法匹配规则的失败连同日志交给 Agent 排查。即使例外很少，也可以只在这部分引入自主决策。

**选用 Agent 后，再决定让它自主做到哪一步。** 能及时发现并撤回的操作，可以交给 Agent 执行。结果难以核验或操作难以撤回时，可以先让它收集证据、提出方案，把执行决定留给有权限的人。

## 指标与测评

验收一次运行，要分别检查**结果是否达标、过程是否合规**。判断能否稳定委托，还要让 Agent 在相同条件下重复执行。

| 指标 | 怎么测 | 回答什么问题 |
| --- | --- | --- |
| 结果达标率 | 核对交付物或环境最终状态，用结果达到验收标准的运行数除以总运行数。 | 有多少次真正办成了任务？ |
| 过程合规率 | 对有过程约束的运行，核对操作及授权记录，统计有证据确认满足全部约束的比例。证据缺失时标为待核实。 | 有多少次能确认执行过程符合要求？ |
| 多次全部成功的任务占比 | 每项任务从相同初始状态独立运行相同次数。只有每次都达标且满足适用约束，该任务才计入分子，分母为任务总数。报告时注明重复次数。 | 有多少任务在多次运行中次次成功？ |

通用测评方法见[[Evaluation|效果评估]]。
