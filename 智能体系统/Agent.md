# Agent

## 概念

### 定义

**智能体（Agent）**是在环境中采取行动的主体。人工智能教材中的这个概念很宽：它不要求使用语言模型，也不要求具有人类式意识。评价重点是主体在目标、信息与资源限制下采取了什么行动。[Poole 与 Mackworth，§1.1](https://artint.info/3e/html/ArtInt3e.Ch1.S1.html)

本文重点讨论**大语言模型智能体（Large Language Model Agent，LLM Agent）**：以[[LLM|LLM]]参与决策，根据目标和执行反馈动态选择后续行动的系统。模型负责理解与选择，外围程序负责组织输入、执行工具、保存状态和控制边界；模型本身不等于完整 Agent。

“Agent”在工程界没有唯一口径。Anthropic 将预先规定执行路径的系统称为工作流，将主要由模型动态决定流程与工具使用的系统称为 Agent。本文沿用这一工程区分，讨论广义概念时另行说明。[Anthropic，What are agents?](https://www.anthropic.com/research/building-effective-agents)

<span style="color: var(--color-red)">理解 LLM Agent，要看模型是否根据反馈决定下一步，以及系统能否将决定转化为可核验的行动。</span>

### 核心价值

Agent 能缓解“任务尚未完成，但下一步无法在开始时写死”的问题。原因是执行会带来新信息，环境也可能变化；系统必须据此修订后续行动。与一次性生成完整方案相比，持续接收反馈为纠错和重新规划提供了机会。[ReAct，§2](https://arxiv.org/html/2210.03629v3#S2)

这个价值有明确前提：反馈能反映任务进展，工具能执行所需动作，完成条件能够检查。反馈错误时，回路可能反复强化错误；权限或工具不足时，规划再完善也无法补齐执行能力。

### 相似概念

| 名称 | 说明 | 优点 | 局限与适用条件 |
| --- | --- | --- | --- |
| 大语言模型 | 根据输入生成内容的模型 | 可理解语言、组织信息与提出行动 | 单独使用时没有外部执行能力；适合输入已充分的生成与判断 |
| 工具调用 | 模型请求外部程序完成指定操作 | 扩展信息获取与执行范围 | 单次调用不证明具有动态任务控制；适合补充特定能力 |
| 固定工作流 | 由预定义规则安排步骤与分支 | 路径容易检查，行为较可预测 | 维护规则有成本；适合流程稳定、分支可枚举的任务 |
| LLM Agent | 模型依据反馈动态选择后续行动 | 能适应执行中新出现的信息 | 路径与成本较难预测；适合确需动态决策的任务 |
| 检索增强生成 | 查找外部资料并用于生成，即 Retrieval-Augmented Generation（RAG） | 改善回答的资料供给 | 不能单独保证行动与闭环；适合依赖外部知识的任务 |

这些概念可以组合。[[RAG|RAG]]可作为 Agent 获取信息的机制；工作流可以包含一个 Agent 环节，Agent 也可以调用固定流程。上表是按控制权与职责进行的概念整理，不是互斥的产品分类。

> [!faq]- A001：LLM Agent 与大语言模型的区别是什么？
> 大语言模型是生成与决策能力的组成部分；LLM Agent 是围绕目标组织模型、执行程序和反馈的完整系统。模型提出行动后，仍需程序执行并把结果反馈回来。是否使用大模型也不是广义 Agent 的定义条件。

> [!faq]- A002：如何区分 LLM Agent 与固定工作流？
> 看后续行动主要由谁决定。工作流遵循预定义路径及分支；LLM Agent 根据目标和反馈动态选择后续行动。调用模型、调用工具或包含循环，都不足以单独划定两者边界，实际系统还可以混合两种方式。

## 工作原理

### 基本过程

**闭环**是行动结果返回决策环节、影响下一步行动的过程。以下是本文为理解工程系统整理的流程；其中权限检查、预算与验收是系统设计要求，不代表每个 Agent 实现都已具备。

![[附件/Agent-执行闭环.png]]

图中①—⑥对应下文步骤；可编辑图源：[[附件/Agent-执行闭环.puml|PlantUML 源文件]]。

1. **明确任务**：将请求整理为目标、限制和验收条件。验收条件规定怎样才算完成；目标不清时应先补齐必要信息。
2. **准备状态**：读取环境观察和已有记录，区分已知事实、推测、已完成事项及待解决事项。这里的状态是系统对任务的记录，不保证等同于环境真实状态。
3. **选择下一步**：模型根据状态决定继续获取信息、执行操作、请求必要输入，或提出结束。计划是可修改的行动安排，不是成功证明。
4. **检查执行条件**：外围程序检查参数是否有效、权限是否允许、预算是否充足。被拒绝的动作返回原因，不能假定已经执行。
5. **执行并回读**：程序调用工具，获得结果或错误，再更新任务状态。若返回值不足以证明目标状态已改变，应补充核验。
6. **验收与退出**：每轮结束时核验实际结果，模型主动提出完成时也要核验；未达标且仍可推进就继续，否则报告未完成状态。预算耗尽、缺少授权和无法恢复的错误也应有明确出口。预算设计应预留最终验收与状态交付所需资源，不能把行动预算用尽等同于目标未达成。

这一回路对应教材中的“观察—控制器—行动”关系。教材还强调：控制器发出的命令与环境里实际发生的行动可能不同，因此需要区分决策、执行与结果。[Poole 与 Mackworth，§2.1](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html)

### 关键组成

| 名称 | 负责什么 | 输入与输出 | 检查重点 |
| --- | --- | --- | --- |
| 目标与约束 | 规定要达成什么、允许做什么 | 用户要求 → 完成标准与边界 | 是否存在冲突或缺失条件 |
| 决策模型 | 理解观察并选择行动 | 当前上下文 → 行动请求或结束提议 | 决定是否有证据、是否推进目标 |
| 执行程序 | 维护回路并落实控制规则 | 行动请求 → 校验、调用、停止或交接 | 权限与预算是否实际生效 |
| 工具与环境 | 提供信息或改变外部状态 | 合法调用 → 观察、结果或错误 | 返回值与真实状态是否一致 |
| 状态与记忆 | 保留当前进展及可复用信息 | 历史记录 → 后续可读取的信息 | 是否过期、失真或漏记 |
| 验收与记录 | 判断完成情况并支持追查 | 运行记录与最终状态 → 判定和证据 | 是否遗漏副作用或错误成功声明 |

**上下文**是本次模型调用实际接收到的信息；**记忆**是保存下来、可在以后调用时取用的信息。外部记忆需要被读取并纳入上下文才会影响本次决策。增加存储空间不等于模型能同时理解全部历史。[Anthropic，Context engineering for long-horizon tasks](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

本文建议将关键进展保存在可核查的任务记录中，而非只依赖模型对对话的概括。保存时写清来源、时间和未决事项，重新使用前检查是否仍有效。是否需要跨任务长期记忆，取决于任务本身，并非 Agent 的必选配置。

> [!faq]- A003：为什么模型说“已经完成”不足以证明任务完成？
> 模型输出是对完成状态的判断，可能与实际执行结果不同。必须核对验收条件、真实环境状态及交付要求；程序返回成功也可能只说明操作被接收。无法核实时，应保留未确认状态，不能把声明当作证据。

> [!faq]- A004：把历史保存为记忆，为什么仍可能丢失任务信息？
> 保存的信息未必被读取进当前上下文；读取后也可能过期、被压缩失真或未被正确理解。因此需要分别检查记录是否完整、当前调用是否取到了必要内容，以及内容是否仍与实际状态一致。

## 能力模型

### 衡量对象

本文将能力指标 **Y 定义为“固定任务集上的合格完成率”**：在统一预算、权限及验收规则下，合格完成的运行数除以全部运行数。一次运行包含其内部全部循环、重试及恢复动作；不把一次工具调用当作一个任务。

这是用于诊断的计数模型，不是论文提出的通用能力公式。取非空任务集，每题运行一次，并预先规定人工参与是否允许。失败、超时、转交都保留在分母中；若某类任务本就以正确转交为目标，应事先写入该类任务的验收条件。

### 从验收条件逐步分解

定义四个数量：

- **N**：全部运行数，N > 0。
- **G**：在规定预算内达到目标结果的运行数。
- **C**：G 中执行过程也满足权限及其他约束的运行数。
- **D**：C 中交付内容也准确、完整并符合要求的运行数。

D、C、G 分别是逐层收窄的运行集合的数量，满足 D ≤ C ≤ G ≤ N。按定义逐步代入：

```text
合格完成率 Y = D / N
合格完成率 Y = (G / N) × (D / G)
合格完成率 Y = (G / N) × (C / G) × (D / C)
合格完成率 Y↑ = 目标达成率↑ × 达成后的过程合规率↑ × 合规后的交付合格率↑
```

第二行要求 G > 0，第三行还要求 C > 0。若 G 或 C 为零，直接报告 Y = 0，对无法计算的条件比例标为“无可用分母”，不要补造比率。箭头只表示**其他因子不变时**的有利方向。

这里分解的是最终验收条件，顺序不表示实际执行先后，也不要求三个因子独立。运行中可以走不同路径，发生错误后也可以恢复；只要最后按同一标准计数，等式就成立。相反，将每次决策正确率简单连乘，会遗漏可恢复错误、路径变化和步骤之间的依赖。

### 优化启示

按验收顺序可将未合格运行分为三组：N−G 是未达目标，G−C 是达标但违反过程约束，C−D 是过程合规但交付不合格。这是分组定位，并不直接证明失败原因。

本文建议回看各组运行记录，将可重复出现的问题对应到流程①—⑥，优先修复影响运行多、可挽回且代价合理的环节。具体对应到流程：

- **目标达成率**：主要回查①目标、②状态、③决策及⑤执行，按失败原因改进输入或动作。
- **过程合规率**：回查④权限校验及⑤实际行为，把必要限制落实到执行程序。
- **交付合格率**：回查⑥验收与最终输出，补齐证据及缺失内容。

每项改动仍需检查是否损害其他因子。

条件通过率低不一定意味着值得最先投入；还要看该组数量、后续条件和修复成本。分母变小也不必然使条件通过率下降。

> [!faq]- A005：为什么不能直接用各步正确率连乘来估计所有 Agent 任务的成功率？
> Agent 的步骤数量和路径可能变化，步骤之间可能依赖，错误也可能被后续动作修复。直接连乘需要额外的路径及条件假设。用合格运行数除以全部运行数衡量整体结果，再按目标、过程和交付条件作嵌套分解，可以容纳这些循环与恢复；但这种分解只是计数关系，不能直接识别因果。

## 关键机制

### 工具把行动请求转为环境操作

**工具**是供 Agent 请求执行的外部程序能力。模型需要知道工具用途、参数含义、结果格式与错误含义。工具边界重叠、描述模糊或返回信息冗余，都可能增加选择与解释难度。[Anthropic，Principles for writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)

本文建议将调用分成三层检查：**请求有效**检查格式及参数，**执行允许**检查权限及状态前提，**结果有效**检查实际效果。三层分别回答“能否理解请求”“能否执行”“是否达成目的”，不能互相替代。

还应处理执行结果不明的情况。**幂等**指同一操作重复执行不会造成额外效果；对于不具备这一性质的操作，超时后应先查实际状态，再决定是否重试。否则，通信失败可能被误判为执行失败，造成重复副作用。这是从执行不确定性推导的工程要求。

### 规划与反馈共同决定下一步

**规划**是根据目标安排动作及其依赖关系。**ReAct（Reasoning and Acting，推理与行动结合）**将语言推理和外部行动交替组织：推理帮助选择行动，行动带回新观察，观察再参与后续判断。论文允许推理根据任务需要稀疏出现，不要求每一步都采用固定三段格式。[ReAct，§2](https://arxiv.org/html/2210.03629v3#S2)

因此，长计划本身不能保证可靠性。本文建议保留目标和约束，对尚未确定的远期步骤保持可调整；每次关键反馈到来后，检查原计划的前提是否还成立。反馈应优先使用可核查的外部证据，不能仅凭模型再次声称自己正确。

### 反思改变后续输入，不必改变模型参数

**反思**是根据执行反馈归纳失败原因和后续改法。Reflexion 方法把这种语言反馈保存在记忆中，供下一次尝试使用；其核心机制不需要更新模型权重。[Reflexion，§3](https://arxiv.org/html/2303.11366v2#S3)

这解释了“行为有所改善”与“模型经过训练”的区别。本文建议保留反思对应的原始证据，并检查后续是否真的避免了同类失败；如果反馈错误或归因错误，反思可能把错误解释持续带入后续运行。

> [!faq]- A006：可靠的工具调用需要检查哪三个层次？
> 请求有效、执行允许、结果有效。分别核对参数与格式、权限与执行前提、环境里的实际效果。任何一层通过都不能代替其他层；结果不明时还需先确认实际状态，避免重试造成重复副作用。

> [!faq]- A007：为什么增加反思步骤不一定提高可靠性？
> 反思依赖反馈和归因是否正确。错误的自评可能形成错误记忆并影响下一次行动。有效反思应能追溯到实际结果，提出可执行改法，并由后续运行验证；文字更长或自信更强不是改善证据。

## 分类

分类应服务于设计选择。以下维度可以组合，并非一条从低级到高级的路线。

| 维度 | 类型与差异 | 选择依据 |
| --- | --- | --- |
| 决策方式 | 直接响应当前观察；先规划再执行；执行中持续重规划 | 信息是否充分、动作依赖是否复杂、环境是否变化 |
| 协作结构 | 单 Agent 集中决策；多 Agent 分工后汇总或交接 | 子任务能否独立推进，结果能否可靠合并 |
| 自主范围 | 仅提出建议；在限定权限内执行；在关键节点请求人工介入 | 动作影响、可恢复性与授权边界 |
| 信息保持 | 仅维护当前运行；增加跨运行的持久记忆 | 后续任务是否需要复用可信历史 |

**多 Agent 系统**是多个智能体协作完成任务的系统，不要求使用不同的基础模型。Anthropic 的研究系统采用主 Agent 分派独立检索方向、子 Agent 回传结果的结构，也指出高度共享上下文、依赖紧密的任务会增加协调困难。[Anthropic，Benefits of a multi-agent system、Architecture overview](https://www.anthropic.com/research/multi-agent-research-system)

据此，本文建议只在任务确可拆分时引入多 Agent：写清每个子任务的输入、交付要求及负责人，再指定谁核验和整合结果。并行能够减少部分等待时间，但会增加计算、通信与整合成本。相同模型和相同资料还可能产生相关错误，因此多个 Agent 同意同一结论，不等于获得多个独立证据。

> [!faq]- A008：什么条件下，多 Agent 比单 Agent 更值得尝试？
> 子任务能相对独立推进，边界和交付要求明确，整合结果所需成本可控，而且并行收益或质量收益足以覆盖额外开销。依赖紧密、频繁修改同一状态的任务可能更适合集中执行。判断应比较整个系统的合格完成率和成本，而不是只看子任务数量。

## 演进与瓶颈

### 关键演进

下面按理解现有设计所需的变化梳理，并非完整技术史，也不表示新方法全面替代旧方法。

- **从控制规则到语言模型决策**：传统 Agent 已有感知、状态、行动与反馈结构。语言模型让自然语言目标与观察能直接参与行动选择，改变的是控制器的实现能力，而非首次发明闭环。[Poole 与 Mackworth，§2.1](https://artint.info/3e/html/ArtInt3e.Ch2.S1.html)；[ReAct，§2](https://arxiv.org/html/2210.03629v3#S2)
- **从单次尝试到利用失败反馈（2023）**：Reflexion 把失败后的反思保存为后续尝试的输入。改善机会从当前运行延伸到下一次尝试，但仍依赖反馈质量。[Reflexion，§3](https://arxiv.org/html/2303.11366v2#S3)
- **从单次成功到重复可靠性（2024）**：τ-bench，即 Tool-Agent-User Interaction Benchmark（工具—智能体—用户交互基准），同时纳入工具、用户交互及规则，并关注重复运行能否持续成功。[τ-bench，§3](https://arxiv.org/html/2406.12045v1#S3)
- **从扩大输入到维护长期状态（2025）**：上下文压缩、外部笔记和子 Agent 分工被系统化用于长任务。关注点是后续决策还能否取到关键事实，而非仅增加上下文容量。[Anthropic，Context engineering for long-horizon tasks](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

| 瓶颈与根因 | 可尝试的干预 | 代价与失败信号 |
| --- | --- | --- |
| 目标理解偏离：验收条件含糊或冲突 | 运行前写清完成标准，补齐决定行动的缺失信息 | 前期交互增加；后续反复改目标说明澄清仍不足 |
| 状态失真：压缩漏记、记忆过期、推测被当事实 | 分开记录事实与推测，保留出处并按需回读 | 增加读写成本；重复劳动或沿用旧条件说明状态维护失败 |
| 执行不可靠：参数错误、服务失败、结果不明 | 改善工具约定，区分错误类型，回查状态后有界重试 | 增加延迟；重复副作用说明重试策略不合格 |
| 反馈失效：只凭自评判断完成 | 用实际结果和明确标准验收，必要时引入人工核查 | 验收也有成本；自报成功但验收失败说明判断偏离 |
| 权限失守：把外部内容误当成行动授权 | 将权限检查置于执行程序，外部材料按数据处理 | 可用动作减少；仅靠提示词约束无法证明边界生效 |
| 循环失控：没有进展判断和退出条件 | 限制预算，识别重复状态，定义停止与交接条件 | 可能提前停止难任务；需检查节约成本是否伴随成功率下降 |

**提示注入**是外部输入夹带指令、试图改变系统原定行为的攻击方式。在上述权限风险中，它说明内容可信度与操作授权必须分开处理：读到某项要求，不代表获得执行该要求的权限。关于防护效果，应单独测试越权动作是否被执行程序阻止，不能仅看模型是否口头拒绝。

> [!faq]- A009：LLM Agent 相比传统智能体，主要改变了什么？
> 主要改变了决策部分：语言模型能够处理自然语言目标、观察与工具说明，并参与动作选择。感知、状态维护、执行和反馈仍是完整系统的基础；引入大模型并不会自动获得可靠执行、长期记忆或权限控制。

> [!faq]- A010：Agent 经常重复行动却不能完成任务，应如何定位问题？
> 先核对目标和验收条件，再检查运行记录：是否重复读取旧状态、遗漏新反馈、工具实际未生效，或没有合法可行的下一步。根据原因修复状态、工具或决策，再检查预算和退出条件。单纯增加轮数可能只延长无效循环。

## 使用场景

Agent 适合的是一组任务条件：**下一步依赖执行中才获得的信息，存在可用行动，反馈可获取，结果可验收，且收益足以覆盖多轮决策成本**。灵活性通常伴随成本与延迟，应与更简单的方案比较。[Anthropic，When (and when not) to use agents](https://www.anthropic.com/research/building-effective-agents)

本文建议按下列顺序选择：

1. **信息齐全且只需生成或判断**：先评估一次模型调用。
2. **主要缺少外部资料**：先评估 RAG 是否足够。
3. **步骤及异常分支稳定**：先评估固定工作流。
4. **后续步骤依赖新反馈**：评估限定权限和预算的 Agent。
5. **独立子任务较多**：以单 Agent 方案作为**基线**，即比较改动效果的初始参照，再评估多 Agent。

若任务结果难以验证、错误后果难以恢复，应缩小自动执行范围，把必要的人类判断纳入流程。这里不是把人工介入视为失败，而是先约定系统应独立完成到哪里，再按同一边界评估。

> [!faq]- A011：是否所有复杂任务都适合使用 Agent？
> 不是。复杂度本身不足以决定架构；还要看步骤是否需要动态选择、工具和反馈是否可用、结果能否验收以及成本是否值得。稳定流程可能更适合工作流，主要缺资料的任务可能只需 RAG。无法可靠验收或恢复时，应缩小自动执行范围。

## 评估与干预

### 指标与测评

**运行轨迹**是一次任务中可记录的模型输出、工具请求、返回结果与状态变化；**最终结果**是运行结束时实际形成的状态。评估既要看结果，也要检查轨迹中的约束遵守情况。规则检查、模型评分与人工评价各有适用范围，模型评分需要**人工校准**，即用人工判定核对评分偏差并据此调整评判方式。[Anthropic，The structure of an evaluation、Types of graders](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

以下是与本文能力模型配套的测评方案。重复测评可组织成多轮，每轮仍对固定题集每题运行一次，分别计算 Y；若汇总全部运行，N、G、C、D 都必须按全部运行重新计数，不能把任务数与运行数混用。

| 指标 | 统计与判定方法 | 结果解释 |
| --- | --- | --- |
| 合格完成率 | D / N；全部运行计入分母，联合检查目标、过程与交付 | 衡量约定边界内的整体效果 |
| 三类验收损失 | 分别记录 N−G、G−C、C−D，并回看对应轨迹 | 帮助定位投入方向，不直接证明根因 |
| 重复可靠性 | 每题在相同配置及重置环境下多次运行，检查持续成功情况 | 区分偶然完成与稳定完成 |
| 约束违反率 | 含至少一次指定违规行为的运行数 / 全部运行数 | 即使最终达标也计入；应单独看严重违规 |
| 成功误报率 | 声称完成但验收失败的运行数 / 声称完成的运行数 | 检查完成判断可信度；分母为零则不报告比率 |
| 单次与单位成功成本 | 总资源成本 / 全部运行数；总资源成本 / D | 同时看调用、等待与人工成本；D 为零时单位成功成本不可计算 |

τ-bench 的 **pass^k**关注同一任务独立重复 k 次全部成功的可靠性；**pass@k**关注 k 次中至少一次成功的可能性。两者回答的问题不同，不能互换。任务难度不同时，也不能把总体平均单次成功率直接取 k 次方来代替 pass^k。[τ-bench，§3，Metrics](https://arxiv.org/html/2406.12045v1#S3)

本文建议同时报告任务构成、运行次数、环境版本、模型与工具配置、预算、人工介入规则。跨设置的分数不宜直接比较；历史基准结果也不能作为当前系统的能力上限。

> [!faq]- A012：为什么 pass@k 提高，仍不足以说明 Agent 可以稳定交付？
> pass@k 只要求多次尝试中至少一次成功，容许其他尝试失败；pass^k 要求重复尝试全部成功，更关注稳定性。比较时还必须统一成功标准、预算、环境及人工介入规则，不能把重复尝试带来的机会增加等同于每次运行更可靠。

### 干预与验证

以下是基于前文能力模型整理的验证步骤，不是某篇论文已证明的通用最优流程。

1. **固定基线**：保留一组代表性任务及初始环境，明确验收条件、预算和配置；记录完整运行，避免只收集成功结果。
2. **定位可修复损失**：按三类验收损失分组，再依据轨迹确定反复出现的原因。优先处理影响大且可验证的改动。
3. **隔离主要改动**：一次验证一个主要假设；保持其他配置尽量一致。重置环境并重复运行，避免状态残留或随机波动造成假改善。
4. **核对整体净收益**：在同一任务集上同时看新增成功与原成功任务的回退。比较目标达成、约束违反、交付质量及成本，不能只优化工具调用次数。
5. **检查适用范围**：用未参与调整的任务复核；小范围使用后观察真实失败。若收益仅存在于调过的题目，或新增成本和风险抵消收益，就不应据此扩大自主范围。

<span style="color: var(--color-red)">Agent 的有效改进，应表现为约定边界内更可靠地完成任务，并有结果、过程与成本证据支持。</span>

> [!faq]- A013：如何验证某项改动真正提高了 Agent 的能力？
> 先固定任务集、环境、预算和验收规则，再比较改动前后的重复运行。核对新增成功是否超过回退，检查过程约束、交付质量与成本，并用未参与调整的任务复核。只有局部指标变好，或仅在调过的任务上成功，都不足以证明整体能力提高。
