# 工具调用

## 概念

### 定义

**工具调用（Tool Calling）**是大语言模型系统通过约定接口请求外部程序，并取得执行反馈的机制。这里的**大语言模型（Large Language Model，LLM）**负责理解输入和生成输出；**工具**是它可请求使用的程序能力；**运行程序**负责连接模型与工具、执行检查并组织反馈。[Anthropic，What is a tool?](https://www.anthropic.com/research/writing-tools-for-agents#what-is-a-tool)

本文讨论[[Agent/Agent|智能体]]中的工具调用机制。智能体是根据目标和反馈选择行动的系统；调用工具也可以嵌入固定流程，并不必然构成智能体。

<span style="color: var(--color-red)">模型提出调用请求，程序落实执行，验收确认任务结果；这三件事不能相互替代。</span>

### 核心价值

工具调用让模型能够获取输入中没有的信息、使用专门计算能力，以及改变外部状态。其根因是语言生成本身不等于读取真实环境或执行操作；工具提供了通向这些能力的接口。

价值成立的前提是：存在可用且获授权的工具，输入足以确定操作对象，反馈能够支持判断。工具返回错误或陈旧信息时，模型仍可能给出错误结论；接入工具不等于获得可靠性保证。

### 相似概念

| 名称 | 说明 | 优点 | 局限与适用条件 |
| --- | --- | --- | --- |
| 函数调用 | 用函数名和参数表达工具请求的常见形式 | 易与程序接口连接 | 参数格式正确仍可能选错对象；适合明确参数的操作 |
| 结构化输出 | 按预定字段与格式生成内容 | 便于程序解析 | 不自带执行效果；适合需要稳定输出结构的任务 |
| 检索增强生成 | 先取回外部资料再生成，即 Retrieval-Augmented Generation（RAG） | 为回答补充资料依据 | 主要解决资料供给；适合依赖外部资料的生成任务；检索可由工具或固定程序触发 |
| 模型上下文协议 | Model Context Protocol（MCP），连接应用与外部能力的通信约定 | 统一工具发现和调用接口 | 不替代模型决策、权限系统和效果验收；适合跨系统接入 |

这些概念属于不同层次，可以组合使用。MCP 规范区分工具返回的结构化数据与模型生成的结构化输出；协议统一的是通信方式，不是任务正确性。[MCP Tools（2025-06-18），Structured Content](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content)

> [!faq]- A001：工具调用中，模型与运行程序分别负责什么？
> 模型根据目标与可见信息提出工具选择和参数；运行程序检查请求、执行工具并回传结果。工具实际改变什么，取决于程序及外部环境。模型说要执行或已经执行，都不能代替执行记录和结果验收。

> [!faq]- A002：为什么结构化输出、工具调用与 MCP 不是同一件事？
> 结构化输出约束生成内容的形式；工具调用把请求交给外部程序执行；MCP 规定应用如何发现和调用外部能力。前者不保证执行，协议不保证选对工具或获得授权，三者可以配合但不能相互替代。

## 工作原理

### 基本过程

下面是本文整理的通用执行回路，包含建议落实的校验与验收，不表示所有产品都已具备这些保障。模型提供商托管工具时，部分执行环节发生在服务端；自建工具则通常由接入方程序执行。[Anthropic，How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)

![[附件/工具调用-执行回路.png]]

可编辑图源：[[附件/工具调用-执行回路.puml|PlantUML 源文件]]。

1. **准备调用条件**：确定目标、验收标准、权限和预算，向模型提供必要的工具定义与任务状态。工具定义说明用途、输入和输出。用于证明访问身份的密钥等凭证由运行程序保管，通常无需暴露给模型。
2. **提出下一步**：模型决定是否调用工具，并生成工具名和参数；也可提出结束。运行程序可以限制工具范围与调用方式，模型并非天然拥有全部选择权。
3. **检查执行条件**：程序检查参数结构、取值含义、操作对象、权限、状态前提和剩余预算。不通过就记录原因，不把拒绝当成已执行。
4. **执行并记录**：将合法请求交给工具，记录返回内容、错误或状态不确定。操作已受理、正在执行和已经完成要分别表示。
5. **关联反馈**：用调用标识把结果对应回请求，并将必要反馈放入下一次模型输入。**调用标识**是区分请求的编号，防止多次或并发调用时结果错配。
6. **核验与退出**：检查目标结果、过程约束和交付内容。未达标且仍可安全推进就返回②；否则报告已完成、未完成或待确认。模型提出结束或行动预算不足时，仍需使用预留资源完成最终验收。

### 关键组成

| 组成 | 作用 | 核查重点 |
| --- | --- | --- |
| 工具定义 | 向模型说明能力边界、输入与返回含义 | 能否判断什么时候应调用、什么时候不应调用 |
| 决策模型 | 提出调用与参数，理解反馈 | 是否选对能力、对象和操作意图 |
| 运行程序 | 校验、调度、关联消息与控制退出 | 是否真正执行权限和预算限制 |
| 工具实现与外部服务 | 读取信息、计算或改变状态 | 接口承诺是否与实际行为一致 |
| 结果与执行记录 | 支撑后续判断、验收和追查 | 能否区分完成、失败与未知状态 |

**上下文**是本次模型实际收到的信息。工具结果只有被纳入上下文，才可能影响下一次生成；结果存在于日志中，不代表模型已看到它。工具定义、结果截取和历史保留可结合[[应用/上下文工程|上下文工程]]设计。

> [!faq]- A003：为什么多次调用需要分别关联请求与结果？
> 多次调用可能访问不同对象，且完成顺序可能与发起顺序不同。运行程序必须保留每个请求的调用标识，并把对应结果反馈给模型；否则模型可能把一个操作的结果误用于另一个操作。

> [!faq]- A004：什么时候可以结束工具调用回路？
> 结果与过程满足验收条件时可以结束；不能继续执行时也必须退出并说明未完成或待确认状态。模型的结束提议只是一个判断，预算耗尽也不是失败证明，两者都应经过最终验收。

## 能力模型

### 衡量对象

本文将 **Y 定义为固定任务集上的合格完成率**。一次运行从接收任务到最终交付，包含全部调用、重试和不调用工具的路径。固定模型、可用工具、权限、预算及验收规则；正确拒绝或正确不调用可按任务预定要求计为成功。

这是本文用于诊断的计数模型，不是通用的模型能力定律。每题先运行一次；若重复运行，应为每题采用相同次数，按全部运行计数，且不要把同一题的重复结果视为完全独立的任务。

### 从验收条件逐步分解

设全部运行数为 N，N > 0；其中在预算内达到目标的数量为 G；G 中过程也合规的数量为 C；C 中最终交付也准确完整的数量为 D。满足 D ≤ C ≤ G ≤ N。

```text
合格完成率 Y = D / N
合格完成率 Y = (G / N) × (D / G)
合格完成率 Y = (G / N) × (C / G) × (D / C)
合格完成率 Y↑ = 目标达成率↑ × 达成后的过程合规率↑ × 合规后的交付合格率↑
```

第二式要求 G > 0，后两式还要求 C > 0；任一条件分母为零时，直接报告 Y = 0，将无法计算的条件比例标为“无可用分母”。箭头仅表示其他因子保持不变时的有利方向。

这是嵌套集合的计数恒等式，不要求各因子独立，也不按执行时间拆分。直接把所有单次调用成功率相乘，会遗漏路径变化、步骤依赖和错误恢复，不能自动代替任务成功率。

### 优化启示

- **目标达成率 G/N**：回查流程①的目标与工具供给、②的选择、③的参数检查、④的执行与⑤的反馈。
- **达成后的过程合规率 C/G**：重点回查③的权限与状态检查，以及④实际发生的副作用。
- **合规后的交付合格率 D/C**：重点回查⑤的证据完整性与⑥的验收、报告。

按 N−G、G−C、C−D 可以定位损失发生在哪类验收条件，但不能仅凭分组确定原因。优先改进影响运行多、可挽回且成本合理的问题；条件比例最低的环节未必最值得先改，进入环节的数量也不等于该环节通过率。

> [!faq]- A005：为什么工具调用成功率高，任务合格完成率仍可能低？
> 调用成功可能只表示请求被接受或程序正常返回；工具可能选错、参数可能指向错误对象，执行过程也可能越权，最终报告还可能不完整。任务合格完成率要求目标、过程和交付同时满足标准，不能由单次调用成功率直接推出。

## 关键机制

### 接口约束结构，业务检查约束含义

**模式（Schema）**是对输入字段、类型和必填条件的结构约定。结构校验能排除部分无效请求，但无法单独证明操作意图正确、对象符合用户要求、当前状态允许操作。

本文建议分层验证：先检查请求结构，再检查参数含义与状态前提，最后根据实际效果验收。即使某种生成机制保证输出符合模式，也不能省去后两层。

### 反馈必须保留可判断的信息

有效反馈应让后续决策知道发生了什么、哪些内容可信、还有什么未确认。过量无关内容会挤占上下文，过度摘要又可能抹去错误、来源与完成状态。工具描述和返回内容应围绕后续决策设计。[Anthropic，Returning meaningful context / Optimizing tool responses](https://www.anthropic.com/research/writing-tools-for-agents#principles-for-writing-effective-tools)

本文建议为结果保留来源或对象标识、状态和必要证据，长结果提供可继续读取的入口；不要把局部截取伪装成完整结果。协议错误表示请求未被通信接口正确处理；工具执行错误表示操作本身失败；任务不达标表示所得效果没有满足目标。三者应分别记录和处理。

### 重试先判断是否已经生效

**幂等性**是同一逻辑操作重复提交不会增加额外副作用的性质。超时只说明调用方未按时拿到结果，不说明服务端没有执行。安全重试需要工具支持的幂等约定，或先核验已有状态。[AWS，Retrying and side effects / Reducing client complexity](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**幂等键**用于让服务端识别重复的逻辑操作，区别于关联模型消息的调用标识。只生成一个键还不够，服务端必须实际识别它，并保证去重记录与操作效果一致。重试同一操作时保留其幂等键；意图变化后不能随意复用。

本文建议先区分参数错误、权限拒绝、暂时故障和执行状态未知：前两类先修正原因，暂时故障在安全前提下有限重试，状态未知先查询或核验。**退避**是逐渐延长重试等待时间，用于减轻故障期间的重复请求压力；它不提供幂等保证。

### 权限由执行系统落实

工具说明是对能力的描述，不是授权凭证。MCP 固定版本规范要求服务端验证输入并落实访问控制，也提醒客户端不能默认信任来自不可信服务的工具行为标注。[MCP Tools（2025-06-18），Tool / Security Considerations](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#security-considerations)

本文建议将权限绑定到用户身份、资源范围和操作类型，由执行程序检查。**提示注入**是外部内容夹带试图改变系统行为的指令；工具返回内容应作为待判断的数据，不能因此自动扩大权限或修改任务目标。只读工具也可能读取并泄露不应访问的信息，因此仍需要访问控制。

> [!faq]- A006：参数符合模式，为什么仍不能直接执行？
> 模式主要约束字段与类型，无法完整判断用户意图、资源权限和当前状态。程序还应校验参数含义、操作对象、权限与状态前提，执行后再核验结果；格式正确只是其中一层条件。

> [!faq]- A007：遇到超时，怎样判断是否应该重试？
> 先确认操作是否已经生效，或者工具是否提供可靠的幂等约定。已生效则复用结果，状态未知且无安全去重机制时不能盲目重做。可安全重试时应限制次数与总时间，并保留同一逻辑操作的幂等键。

> [!faq]- A008：为什么不能把工具返回的指令当作新的授权？
> 工具结果可能来自不可信外部内容，也可能夹带提示注入。它提供的是任务数据，不天然拥有用户或系统的指令权限。授权仍需由既定身份、资源范围和操作规则决定，执行程序负责落实。

## 分类

分类对象是工具及其执行安排；下列维度可以交叉组合，不能混为一条等级序列。

| 维度 | 类型与差异 | 选择条件与局限 |
| --- | --- | --- |
| 状态影响 | 只读操作读取信息；写入操作改变外部状态 | 写入尤其需要核验副作用与重试语义；只读仍有数据访问风险 |
| 执行位置 | 接入方执行；模型提供商托管执行 | 影响谁维护程序和执行边界，不改变验收责任 |
| 任务依赖 | 串行等待前序结果；并行同时推进独立操作 | 并行要同时检查数据依赖、共享状态冲突和资源限制 |
| 完成方式 | 同步返回完成结果；异步先返回任务标识 | 异步需要后续查询或完成通知，受理不等于完成 |

本文建议只在参数无需依赖彼此结果、共享状态不会冲突且权限允许时并行。否则应先完成依赖步骤，再依据结果发起后续操作。并行能缩短部分等待时间，但不保证总成本更低。

> [!faq]- A009：哪些条件决定工具调用能否并行？
> 后续请求是否依赖前序结果、操作是否竞争同一状态，以及服务和预算是否支持并发。仅仅使用不同工具名并不能证明独立；存在依赖或冲突时，应串行执行或由程序提供一致性控制。

## 演进与瓶颈

### 关键演进

工具调用的演进包含决策方式、训练方式与接入方式的变化，以下并不是彼此替代的版本链。

- **ReAct（2022）**：名称组合了推理（Reasoning）与行动（Acting）。将推理与行动交错，让外部观察影响后续决策。变化在于可以根据反馈调整行动；它不自动保证工具可靠、执行获授权或最终达标。[ReAct，§2](https://arxiv.org/html/2210.03629v3#S2)
- **Toolformer（2023）**：通过构造并筛选工具调用数据，让模型学习何时调用、传什么参数以及怎样使用结果。它展示了训练工具使用行为的路径；效果取决于训练数据、工具范围和评估任务。[Toolformer，§2](https://proceedings.neurips.cc/paper_files/paper/2023/file/d842425e4bf79ba039352da0f658a906-Paper-Conference.pdf)
- **标准化工具接入**：MCP 将发现工具、描述输入输出和调用组织为统一协议。它减少连接方式差异，但不会自动解决选择错误和执行风险。本文引用固定的 2025-06-18 规范说明机制，不把它作为最新版本声明。[MCP Tools，Listing Tools / Calling Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#protocol-messages)

### 当前瓶颈

- **工具多但边界不清**：模型难以区分用途，增加误选与无效调用。可收窄当前可见工具、明确功能边界；代价是筛选阶段可能漏掉必要能力，必须检查工具覆盖与最终成功率。
- **调用正确但反馈不足**：结果缺少来源、状态或完整性说明，后续推理容易失真。可改善返回格式并提供继续读取入口；代价是更多上下文与读取成本。
- **单步成功但多步不一致**：环境变化、并发冲突和重试重复生效破坏整体结果。可通过状态检查、幂等处理和结果回读减轻问题；这些保障依赖工具实现，不能仅靠提示词承诺。
- **控制更严但任务更难完成**：约束可以减少越权，也可能误拦合法操作。应同时衡量合规和目标达成，不能把全面拒绝误当成整体改进。

以上是结合前文机制提出的诊断框架，具体效果需在目标任务上验证，不代表所有系统都存在同样瓶颈。

> [!faq]- A010：ReAct、Toolformer 与协议标准化分别改变了什么？
> ReAct 改变运行时推理、行动和观察的组织方式；Toolformer 研究通过训练学习工具使用行为；协议标准化改善外部能力的发现与通信。它们分别作用于决策回路、模型学习和系统接入，可以组合，不能相互替代。

> [!faq]- A011：增加工具为什么可能降低任务完成率？
> 当新增工具与现有工具用途重叠、描述不清或占用过多上下文时，选择与反馈解释会更困难。应核对新增能力是否覆盖真实缺口，再在同一任务集比较新增成功与原本成功的任务是否变为失败，而非仅统计工具数量。

## 使用场景

适合工具调用的条件是：任务确实依赖外部信息、专门计算或状态操作，且系统具备可用工具、合法权限和可核验结果。涉及动态决策时，反馈还需要足以支持下一步选择。

如果输入已经充分、任务只需组织表达，额外调用可能只增加延迟与失误机会。如果流程稳定且规则能够明确表达，可由固定程序安排调用，无需把每一步都交给模型决定。没有必要权限或无法确认关键执行结果时，应补齐条件或交接，不应把工具缺口转写成成功声明。

> [!faq]- A012：怎样判断是否需要让模型参与工具选择？
> 先判断任务是否需要外部能力，再判断调用路径是否必须根据新信息动态变化。需要外部能力但流程稳定时，可以由固定程序调用；路径确实依赖反馈时，才有理由让模型参与选择，并配置相应的校验与验收。

## 评估与干预

### 指标与测评

[[应用/Evaluation|评估]]应先判断真实结果，再用调用记录定位原因。允许多条合法完成路径，不要求系统机械复现唯一调用序列。Anthropic 的工具评估指南同样强调可核验结果、真实任务和运行成本。[Anthropic，Running an evaluation](https://www.anthropic.com/research/writing-tools-for-agents#running-an-evaluation)

以下指标是本文建议的测量口径；统计调用时包含失败与重试，统计任务时则把整个回路视作一次运行。

| 指标 | 分母与计入条件 | 用途与限制 |
| --- | --- | --- |
| 合格完成率 | 全部运行中，同时通过目标、过程和交付验收的比例 | 比较整体效果，包含正确不调用与正确拒绝路径 |
| 调用决策正确率 | 有预先判定标准的决策点中，需要时调用且不需要时不调用的比例 | 检查调用时机；应分别报告漏调用和多余调用 |
| 参数有效率 | 全部调用请求中，结构与业务语义检查都通过的比例 | 检查接口与参数理解，不证明最终达标 |
| 执行效果达标率 | 实际发出的请求中，观察期内达到工具约定效果的比例 | 超时且状态未知单列，不能当作明确未执行 |
| 过程违规率 | 全部运行中发生越权或其他预定禁行行为的比例 | 不只检查最终状态；与目标达成一起解释 |
| 延迟与资源消耗 | 每次完整运行的耗时、调用数及模型处理量 | 同时报成功和失败运行，避免只统计成功样本 |

测评集应包含应调用、不应调用、信息不足、权限不足、暂时故障、状态未知和有依赖的多步任务。预先规定未知状态的观察期限；期限内未确认合格的运行保留在总分母中，同时单列原因。

离线检查请求格式可以诊断接口问题，但不能代替真实环境中的效果检查。模型自述与工具返回成功标志也不能独立充当验收标准；应核对可靠记录或外部状态，并明确测量仍未覆盖的部分。

### 干预与验证

1. **建立基线**：固定任务集、环境起点、模型版本、权限与预算，记录每次运行的结果和调用过程。另留未参与调试的任务，检验是否只适应了已见题目。
2. **定位损失**：先按目标、过程和交付分组，再检查具体调用轨迹。分清工具缺失、误选、参数错误、执行故障与结果误读，不从单个比例直接推断原因。
3. **实施干预**：工具误选优先改边界和描述；参数错误优先改字段含义与校验；反馈误读优先改返回；重复副作用优先改幂等与状态核验。选择影响范围清楚、可回退的改动。
4. **对照验证**：在相同条件下重跑，并核对合格完成率、违规率与成本。固定任务集的成功数变化等于新增成功数减去原有成功的回退数；局部指标上升不保证净收益为正。

<span style="color: var(--color-red)">优化目标是以可接受的成本合规完成任务，而不是让模型调用更多工具，或让每次请求都显示成功。</span>

> [!faq]- A013：为什么评估不能只比对工具名和参数？
> 正确任务可能存在多条合法路径，而形式正确的请求也可能没有实际生效。工具名和参数检查用于定位决策问题；整体评估还必须核验外部效果、过程约束与交付，并计入失败、未知状态和成本。

> [!faq]- A014：怎样证明一次工具改造改善了系统？
> 在任务、环境、权限、模型和预算保持一致的条件下，与原版本比较合格完成率、违规率及成本，再用未参与调试的任务验证。查看新增成功是否超过原有成功的回退，确认收益来自真实结果，而非只来自更好看的格式或调用指标。
